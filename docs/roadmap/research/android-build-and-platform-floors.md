# Android build form and platform floors (N5, decision D3)

Research date: 2026-10-11. Researcher N5. Tools used: `gh api` against pinned tags, WebFetch, WebSearch. Firecrawl was not used (low credits). Citation rule: documents by section, code by symbol at a pinned tag or commit, never by line number.

## 1. Question

As of October 2026, how should a Kotlin Multiplatform library publish its Android artifacts (the Android-KMP library plugin `com.android.kotlin.multiplatform.library` versus `com.android.library` with `androidTarget()`, AGP 9 constraints, AAR publishing to Maven Central with the vanniktech plugin), and what minSdk and other Android platform floors should SpartanGraphics' Android backend adopt?

Decision it informs: D3, the target architecture's module form on Android (`graphics-android`, `audio-android`, Android source sets inside KMP modules such as `assets`), the minSdk open decision, and the Android build constants (JVM 21 bytecode, toolchains, desugaring).

## 2. Bottom line

- **`androidTarget()` with `com.android.library` is a dead end on AGP 9.** AGP 9.0+ makes the KMP plugin incompatible with `com.android.library`/`com.android.application` in the same subproject; the old APIs are opt-in-only in 9.x and removed in AGP 10.0 (announced for late 2026). KGP 2.4.0's own KDoc on `androidTarget()` says to use `com.android.kotlin.multiplatform.library`. Use the new plugin for any KMP module that needs an Android target (the `assets` module). Established consensus (Google, JetBrains, and Ktor, SQLDelight and Coil all do it).
- **Android-only device-family modules (`graphics-android`, `audio-android`) should be plain `com.android.library` modules** (AGP 9 built-in Kotlin, new DSL, single-variant release AAR via vanniktech `AndroidSingleVariantLibrary`), not KMP modules with one Android target. AGP 9 only forbids *KMP plus* `com.android.library`; plain `com.android.library` is not deprecated. Coil 3.6.3 publishes its non-KMP Android modules exactly this way. This is a judgment call (common practice, not a stated rule); the alternative (one-target KMP module) works but doubles the artifact name suffix.
- **Pure-common KMP modules (`graphics-core`, `audio-core`) need no Android target.** KGP ships a Gradle compatibility rule that lets an `androidJvm` consumer take a `jvm` variant (`KotlinPlatformType.CompatibilityRule`), which is how `kotlinx-coroutines-core` and most of Ktor reach Android. Declaring an Android target would only be justified to get Android lint / `android.jar` API checking, and the Ktor project shows the cost (every contributor then needs an Android SDK).
- **Recommended minSdk: 24, compileSdk 37 (latest AGP 9.4 supports), targetSdk left to apps.** 24 is the AndroidX default today, makes `PointerIcon` (API 24) unconditional, and reaches about 96.6% of Android web traffic (Statcounter, April 2026) and, by Google's stated intent for its default, about 99% of Play check-ins. Nothing on the roadmap needs a higher floor: GLES 3.0 is API 18, `SoundPool.Builder` API 21, and the API 26+ and 29+ items (`AudioFocusRequest`, AAudio, `Font.Builder(ByteBuffer)`, `androidx.webgpu`) and API 31 `TextRunShaper` are runtime-gated capabilities. Lowering a library minSdk later is compatible; raising it is breaking, so start at 24 and lower only if a consumer asks. Final call is the user's (see Gaps).
- **JVM 21 bytecode on Android is the one unproven build constant.** Google's own Java-version table stops at Java 17 (Android 14), I found no document that says D8 accepts class-file version 65, and no sampled comparable (Ktor, libGDX, coroutines) ships bytecode above its Java 8 to 17 baseline. Make a sample-app dexing and R8 job the gate (Q5 already requires the sample), compile Android-consumable `jvm` variants with `-Xjdk-release`, and have a fallback (lower `jvmTarget` for the Android-consumed modules only) ready.

## 3. Findings

**F1. The Android-KMP library plugin is the supported path; the legacy combination is being removed.** Tier: established consensus (vendor docs from Google and JetBrains, plus KGP source).
- Android docs, "Set up the Android Gradle Library Plugin for KMP": the plugin is "the officially supported tool for adding an Android target to a Kotlin Multiplatform (KMP) library module"; minimum AGP 8.10.0 and KGP 2.0.0. It "uses a single variant, removing support for product flavors and build types"; Java compilation, unit tests and device tests are off by default and opt-in (`withJava()`, `withHostTest {}`, `withDeviceTest {}`); `res` folders need `androidResources { enable = true }`; `BuildConfig`, data/view binding and `externalNativeBuild` are unsupported; consumer keep rules must be published explicitly with `optimization.consumerKeepRules.publish = true`. [Plugin page](https://developer.android.com/kotlin/multiplatform/plugin), fetched 2026-10-11.
- The same page states the legacy `com.android.library` APIs used for KMP "are deprecated and require opt-in in Android Gradle plugin 9.0 and higher" and "are expected to be removed in Android Gradle plugin 10.0 (second half of 2026)".
- DSL name churn: the extension is `kotlin { android { ... } }` from AGP 8.12; `androidLibrary {}` "is deprecated since AGP 9.1.0-alpha09". The kotlinlang pages still show `androidLibrary {}` ([KMP AGP 9 migration](https://kotlinlang.org/docs/multiplatform/multiplatform-project-agp-9-migration.html)); use `android {}`.
- KGP 2.4.0 source: the KDoc on every `androidTarget(...)` overload in `KotlinTargetContainerWithPresetFunctions` says the multiplatform plugin "will not be compatible with most of the Android Gradle plugins from Android Gradle Plugin version 9.0.0. Please use the 'com.android.kotlin.multiplatform.library' plugin instead." [JetBrains/kotlin @ v2.4.0](https://github.com/JetBrains/kotlin/blob/v2.4.0/libraries/tools/kotlin-gradle-plugin/src/common/kotlin/org/jetbrains/kotlin/gradle/dsl/KotlinTargetContainerWithPresetFunctions.kt).

**F2. AGP 9.x facts that constrain the build.** Tier: established consensus (vendor docs).
- AGP 9.0 enables built-in Kotlin by default, has a runtime dependency on KGP 2.2.10 (auto-upgrades lower KGP), minimum Gradle 9.1.0, JDK 17. [AGP 9.0.0 release notes](https://developer.android.com/build/releases/agp-9-0-0-release-notes), sections "Built-in Kotlin" and the compatibility table.
- AGP 9.4.0 (September 2026): minimum and default Gradle 9.6.0, SDK Build Tools 36.0.0, JDK 17, maximum API level 37. [AGP 9.4.0 release notes](https://developer.android.com/build/releases/gradle-plugin), compatibility table. This sets the Gradle wrapper floor for this repo if it uses AGP 9.4.
- Roadmap: AGP 10.0 (late 2026) removes the opt-out flags `android.newDsl` and `android.builtInKotlin`, so "the modern DSL and built-in Kotlin are strictly enforced". [Roadmap](https://developer.android.com/build/releases/gradle-plugin-roadmap). The page gives only estimates.
- Kotlin 2.4 needs AGP 8.5.2+ (R8 9.1.29). [AGP/D8/R8 versions required for Kotlin](https://developer.android.com/build/kotlin-support).
- I found no AGP 10 alpha release notes (search 2026-10-11).

**F3. Publishing to Maven Central with vanniktech works with both plugin forms.** Tier: common practice (plugin docs plus two large projects).
- vanniktech 0.37.0 (2026-06-21) docs, "Kotlin Multiplatform Library": "The `com.android.kotlin.multiplatform.library` plugin does not need any special configuration. When using it leave out the third parameter (`androidVariantsToPublish`) of `KotlinMultiplatform`." Support was added in 0.35.0 (2025-11-11). Minimum: JDK 17, Gradle 9.0.0, AGP 8.13.0, KGP 2.2.0. Tested up to AGP 9.2.1 / 9.3.0-rc01 / 9.4.0-alpha01, Gradle 9.6.0, KGP 2.4.0. [docs/what.md @ 0.37.0](https://github.com/vanniktech/gradle-maven-publish-plugin/blob/0.37.0/docs/what.md), [0.37.0 release](https://github.com/vanniktech/gradle-maven-publish-plugin/releases/tag/0.37.0), [0.35.0 release](https://github.com/vanniktech/gradle-maven-publish-plugin/releases/tag/0.35.0).
- For plain `com.android.library`, the docs section "Android Library (single variant)" gives `AndroidSingleVariantLibrary(javadocJar, sourcesJar, "release")`. Dokka v1 support was removed in 0.36.0; use Dokka v2.
- Android's own page: with the new plugin "There are no Android-specific steps required beyond the standard KMP library publishing process."
- Ktor 3.6.0 pins `mavenPublishing = "0.37.0"` with `android-gradlePlugin = "9.4.0"` in `gradle/libs.versions.toml`, so the combination is in production (with the KMP plugin; the legacy `AndroidSingleVariantLibrary` path under AGP 9.4 I did not see exercised, see Gaps).

**F4. A `jvm()`-only KMP module is consumable from Android without an Android target.** Tier: established mechanism (KGP source plus Gradle docs), common practice (coroutines, Ktor).
- KGP v2.4.0, `KotlinPlatformType.CompatibilityRule.execute`: `if (producerValue == jvm && consumerValue == androidJvm) compatible()`. [KotlinPlatformType.kt @ v2.4.0](https://github.com/JetBrains/kotlin/blob/v2.4.0/libraries/tools/kotlin-gradle-plugin-api/src/common/kotlin/org/jetbrains/kotlin/gradle/plugin/KotlinPlatformType.kt).
- Gradle's `TargetJvmEnvironment` does "NOT strictly require environments to match, as the general assumption is that Java libraries can also run on environments they are not optimized for." [javadoc](https://docs.gradle.org/javadoc/org/gradle/api/attributes/java/TargetJvmEnvironment.html).
- `kotlinx-coroutines-core` @ 1.11.0 has no Android target in its build (only `androidNative` source-set grouping); Android uses its `jvm` variant. Ktor 3.6.0 applies `com.android.kotlin.multiplatform.library` only through the opt-in convention `ktorbuild.optional.android-library` (its minSdk 28 constant is used by `ktor-client-webrtc`); the other modules rely on `jvm`.
- Consequence: nothing checks that a `jvm` variant only uses APIs Android has. Android lint in the consuming app does not look inside dependency jars (my understanding; not verified, see Gaps). Jake Wharton (2024-03-13): with a JDK 21 build, `list.removeFirst()` "accidentally took precedence" over the Kotlin extension and crashed older Android runtimes with `NoSuchMethodError`; fix is `-Xjdk-release`, and "setting `jvmTarget` alone isn't enough". [Post](https://jakewharton.com/kotlins-jdk-release-compatibility-flag/). Tier: one expert source, mechanism corroborated by the Kotlin compiler test data (`compiler/testData/cli/jvm/XjdkRelease` @ v2.4.0 shows `-Xjdk-release=7` with `-jvm-target 1.8` restricting the API surface, while `-Xjdk-release=1.6` with `-jvm-target 9` is rejected).

**F5. Distribution data (the Google dashboard no longer gives it).** Tier: common practice; the number is third-party web-traffic data, not Play data.
- The Google dashboards page (page updated 2026-10-06; data window ending 2025-11-24) now carries only Vulkan and OpenGL ES tables, and points to Play Console "Reach and devices" for OS-version data. I could not obtain a first-party API-level table.
- apilevels.com, cumulative, "last updated on May 28, 2026 using April 2026 data from Statcounter GlobalStats": API 21+ 99.8%, 23+ 98.0%, 24+ 96.6%, 26+ 96.1%, 28+ 93.5%, 31+ 78.8%, 33+ 68.9%, 36 22.3%, 37 0%. [apilevels.com](https://apilevels.com/).
- The step from 24 to 26 is 0.5 points; the step from 23 to 24 is 1.4 points; from 21 to 23 is 1.8 points.
- AndroidX: "AndroidX libraries have the default `minSdk` of 24. The default `minSdk` is meant to cover 99% of Android users based on the Google Play Store check-in information, as is shown in Android Studio's New Project wizard. The default value is updated at a yearly cadence." [Jetpack versions, "Minimum SDK Version"](https://developer.android.com/jetpack/androidx/versions). A localized copy of the same page showed 23, so the value changed at least once recently; read the English page.

**F7. Consumer expectations on an AAR/JAR.** Tier: vendor docs.
- AAR: `consumerProguardFiles("consumer-proguard-rules.pro")` in `defaultConfig`. JAR: rules go in `META-INF/proguard/`; version-targeted rules go in `META-INF/com.android.tools/r8-from-<X>-upto-<Y>`. Libraries "must not include broad keep rules" and must never use `-dontobfuscate` or `-allowaccessmodification`. [Library optimization](https://developer.android.com/topic/performance/app-optimization/library-optimization). Backends that reflect (the planned `PointerIcon` fallback) need narrow rules.
- `namespace` is required by AGP 8+ libraries and must be distinct per module; AGP 9 KMP guidance says use a distinct namespace for the shared library so it does not conflict with the app's ([KMP AGP 9 migration](https://kotlinlang.org/docs/multiplatform/multiplatform-project-agp-9-migration.html), step 4).

**F8. JVM 21 bytecode on Android.** Tier: weak / unresolved.
- Google's "Java versions" table maps Android 12/13 to Java 11 and Android 14 (API 34) to Java 17, and ends there ([JDKs in Android builds](https://developer.android.com/build/jdks)). AGP 8.x/9.x need JDK 17 to run.
- Language features are desugared by D8; APIs are not (needs `compileSdk` plus desugaring: "If you use a Java API that's available in a `compileSdk` that's not available in the specified `minSdk`, you might be able to use the API ... through ... desugaring"). Desugar "doesn't support `MethodHandle.invoke` or `MethodHandle.invokeExact`... you need to specify `minSdkVersion 26` or higher" ([Java 8+ support](https://developer.android.com/studio/write/java8-support)); a floor of 24 means no code in our artifacts or their dependencies may use those.
- R8's `CfVersion` on main defines constants through `V21` (and beyond, to `V27`) ([r8.googlesource.com](https://r8.googlesource.com/r8/+/refs/heads/main/src/main/java/com/android/tools/r8/cf/CfVersion.java)). That shows the reader recognises those versions on main; it does not tell which bundled D8 first accepted 65, or whether any limit applies for AGP 9.4's bundled D8.
- Kotlin side: a library compiled for a higher `jvmTarget` than its consumer breaks inline-function inlining ("Cannot inline bytecode built with JVM target X into bytecode being built with JVM target Y"), a well-known error in older threads. Android Studio's template consumers commonly sit at 11 (my recollection, unsourced), so a 21-target library forces consumers up. Tier: forum evidence (old), mechanism still true by design.

## 5. Pitfalls and regrets

- **KMP plus `com.android.library` stops working at AGP 9.0**, and the temporary opt-in property `android.enableLegacyVariantApi=true` goes away with AGP 10 ([Kotlin migration page](https://kotlinlang.org/docs/multiplatform/multiplatform-project-agp-9-migration.html)). Do not start new modules on `androidTarget()`.
- **The new KMP plugin drops features by design**: no build types or flavors, no `BuildConfig`, no JNI builds, resources off by default. Anything needing those goes into a separate plain `com.android.library` module. Consumer keep rules do not publish unless `optimization.consumerKeepRules.publish = true`.
- **Library minSdk above a consumer's minSdk fails the consumer's manifest merge** (the Compose 1.10.2 report in the Kotlin Slack is one public example; it is a secondary source). Raising a floor is breaking; lowering is not. Both SQLDelight and libGDX shipped floor bumps as changelog items.
- **Compiling `jvm` variants with a JDK 21 classpath leaks JDK 21 APIs** (`List.removeFirst`/`removeLast` and the other `SequencedCollection` members) into code that must run on Android 14 or lower. `jvmTarget` does not stop it.
- **Statcounter and Play disagree**: 24+ is 96.6% on web traffic but "99%" in Google's stated intent for the AndroidX default. Pick the number's source consciously. Google no longer publishes OS version shares on the public dashboard page.
- **Plugin windows lag AGP**: vanniktech 0.37.0 documents tests up to AGP 9.3.0-rc01 / 9.4.0-alpha01, yet Ktor runs it with AGP 9.4.0. Pin and test; do not assume.
- **Requiring an Android SDK for every build** is a contributor cost. Ktor made the Android target conditional on the SDK being present and prints an actionable problem; SpartanGraphics' per-device modules make the same split natural (only the `*-android` modules and `assets` need the SDK).
- **Naming**: a one-target KMP module named `graphics-android` would publish an Android artifact id of `graphics-android-android` (target suffix; my inference from KMP's artifact naming, not verified here). A plain Android library avoids it.
- **`androidx.webgpu` is alpha with min API 26**; do not design the floor around it.

## 6. Recommendation for this repo

**Module form.**
- `graphics-android`, `audio-android`: plain `com.android.library` (AGP 9.4.x, built-in Kotlin, new DSL, no `org.jetbrains.kotlin.android` plugin), one release variant, AAR via vanniktech `AndroidSingleVariantLibrary`. They depend (`api(project(...))`) on the pure-common modules, which resolve to the `jvm` variant. These are Android-only code (GLSurfaceView, `SoundPool`, `PointerIcon`), so a KMP shell adds nothing; this matches the split plan's rule of one module per device family and keeps `graphics-desktop` and `graphics-android` structurally symmetric (both single-platform modules).
- `assets`: KMP with `jvm()`, the Android target from `com.android.kotlin.multiplatform.library` (`kotlin { android { namespace = "io.github.spartanlaboratories.assets"; compileSdk; minSdk } }`, `androidMain` with the `AssetManager` loader), and later the web target. Published with `com.vanniktech.maven.publish`, `KotlinMultiplatform(...)` without the `androidVariantsToPublish` argument.
- Pure-common modules (`graphics-core`, `audio-core`, others): `jvm()` plus web targets, no Android target. Reasoning: the compatibility rule makes it work, the dominant comparables do it, and an Android target would force an SDK on every build for no runtime benefit. Revisit only if you want `android.jar` API checking inside common code (alternative: `-Xjdk-release` plus a dexing job in the sample app, below).
- Convention plugins in `build-logic` (names illustrative): `spartan.kotlin-jvm`, `spartan.kotlin-multiplatform`, `spartan.android-library` (applies `com.android.library`, sets `namespace` from the module name, `compileSdk`, `minSdk` from the version catalog, `consumerProguardFiles`, vanniktech single-variant publication), and `spartan.android-kmp-target` (applies the KMP Android plugin, same constants, `optimization.consumerKeepRules.publish = true` only if the module ships rules). Put AGP on `build-logic`'s classpath once through the catalog (`implementation(libs.agp)`) and apply plugins by id without versions in modules (Coil and Ktor both do this). Put `minSdk`, `compileSdk` and the JDK level in `libs.versions.toml` as single constants. Do not cargo-cult Coil's legacy `androidLibrary()` helper structure (`LibraryExtension` plus `sourceSets["main"]`) beyond what the new DSL needs.

**minSdk 24; compileSdk 37; no targetSdk in libraries** (the sample app sets its own). Reasoning: the floor is the AndroidX default (aimed at 99% of Play check-ins; 96.6% on Statcounter web traffic), `PointerIcon` and Java 8 default/static interface methods then need no guards, and GLES 3.0 is already two levels below. 26 buys only 0.5 points of reach loss for `AudioFocusRequest`, `Typeface.Builder` and `java.time`, none of which is worth a hard floor: `AudioFocusRequest` has an older call path, and the rest are optional. 23 or 21 (Coil and SQLDelight at 23, libGDX at 21) widen reach by 1.4 and 3.2 points but make `PointerIcon` a guarded or reflective path and keep `minSdk < 24` desugaring concerns for consumers. Gate the following at runtime on `Build.VERSION.SDK_INT`: `AudioFocusRequest` (26), `Font.Builder(ByteBuffer)` (29), `TextRunShaper` (31). Do not adopt `androidx.webgpu` before it leaves alpha.

**Other floors and constants.**
- Toolchain: JDK 21 for building (AGP needs 17+). Gradle wrapper at least 9.6.0 if AGP 9.4 is used. Kotlin 2.4.x. vanniktech 0.37.0 or newer.
- Desugaring: do not enable `coreLibraryDesugaring` in the library; keep to APIs at or below API 24 in `*-android` code (no `java.time`, no `MethodHandle.invoke`); consumers who need more can enable it in their app. (The "library should not force desugaring" statement is my recommendation; I did not find a Google rule stating it.)
- JVM 21 bytecode: keep 21 as the default for desktop-only modules. For modules whose `jvm` variant an Android app can consume, pass `-Xjdk-release` at the level you want to promise (candidate: 17, which is Android 14's Java level) as a raw Kotlin compiler argument (I did not confirm a Gradle DSL property in 2.4). Add a CI job that builds the Android sample app (Q5) at `minSdk=24` with `assembleRelease` (R8 on, so D8 dexes every dependency JAR); if D8 or consumers' inlining reject class version 65, lower only the Android-consumed modules' `jvmTarget` (to 17) rather than the whole repo. This changes a binding constraint ("libraries target JVM 21") for a subset, so it needs your decision if the spike fails.
- Consumer rules: ship `consumer-proguard-rules.pro` in each `*-android` AAR for anything reflective (the `PointerIcon` fallback); narrow keep rules only.
- Conditional SDK: follow Ktor and apply the Android convention only when `ANDROID_HOME` or `sdk.dir` is set, so desktop and web contributors do not need the SDK.

Rejected: `androidTarget()` plus `com.android.library` (removed in AGP 10, incompatible in 9); one KMP module per platform for graphics (contradicts the split plan and adds the KMP shell for Android-only code); an Android target on every common module (cost with no demonstrated benefit).

## 8. Gaps

- **JVM 21 class files through D8 are unverified.** I could not find a Google statement that D8/R8 in AGP 9.4 accepts class-file version 65 (only that R8 main defines `CfVersion` constants to `V27`, and Google's Java table stops at 17). Nor did I find which AGP first accepted it. The consumer-inlining cost (consumers at `jvmTarget` 11 or 17) is old forum evidence plus my reading of compiler behaviour. This blocks only one sub-decision of D3 (whether Android-consumed modules keep 21); the proposed spike settles it.
- **Does AGP set `org.gradle.jvm.version` on Android compile/runtime classpaths?** If yes, a `jvm` variant published with `jvm.version=21` could be rejected or ignored on resolution for an Android consumer with a lower Java level. I found no source either way (search 2026-10-11); the Kotlin Slack thread I found on "how jvm level works with library development" returned HTTP 429. The same spike (an Android app consuming the `jvm` variant at `jvmTarget` 21) tests it.
- **Android lint does not scan dependency jars for NewApi** is my understanding, not sourced. If wrong, the `-Xjdk-release` plus CI job matters less.
- **No first-party API-level distribution** is available any more on the public dashboard page; all reach numbers are Statcounter via apilevels.com (web traffic, April 2026). Google Play's "Reach and devices" would settle it but needs a Play Console account.
- **The official Android reference pages for `PointerIcon`, `TextRunShaper`, `Font.Builder`, `Typeface.Builder` did not render in my fetch tool** (it returned only the navigation for 300k+ characters). The "Added in API level" values for `PointerIcon` (24, also in `cross-platform-input.md`), `TextRunShaper` (31), `Font.Builder(ByteBuffer)` (29) and `Typeface.Builder` (26) come from search-engine extractions of those pages, backed for 31 by the AndroidX source comment and for the constructor sets by AOSP source. `Typeface.createFromFile` being API 1 is from memory.
- **`AndroidSingleVariantLibrary` under AGP 9.4** (plain `com.android.library` publication) was not seen working in a project I could read; vanniktech 0.37.0 lists tests up to AGP 9.3.0-rc01/9.4.0-alpha01 only. Ktor runs 0.37.0 with AGP 9.4.0 but through the KMP plugin. Coil's AGP version was not read. Before committing to plain `com.android.library` for `graphics-android`, publish one test artifact to a local repo with the pinned versions (a mutation I did not and may not do).
- **The Kotlin DSL for `-Xjdk-release`**: Wharton's 2024 post says there was no DSL (KT-49746). I did not confirm the 2.4 state; assume a raw compiler argument. The test data shows `-Xjdk-release=1.6 -jvm-target 9` is rejected, so whether `-Xjdk-release=17 -jvm-target 21` is accepted must be tested.
- **Not sampled:** Compose Multiplatform's Android floor (only a secondary Slack/Zendesk report of 23), KorGE's actual minSdk, why Kool's Android target is commented out, the `aarMetadata.minCompileSdk` default for libraries built with `compileSdk = 37` (whether consumers on lower compileSdk are blocked), and whether the new KMP plugin supports Dokka v2 Android sources without extra setup (Coil's `setupDokka` runs against it, so likely yes).
- **Brief gaps:** the split plan (`docs/plans/spartan-libraries-split.md`) and the draft architecture were not re-read; I relied on the brief's summary. The user's repo toolchain (Gradle patch version, Kotlin version) is not known, so the Gradle 9.6.0 floor for AGP 9.4 is stated as a constraint to check.
- **User decision needed (not mine):** the minSdk value (24 recommended; 23 and 26 are defensible), and whether a failed JVM 21 dexing spike may relax the "JVM 21" rule for Android-consumed modules.
