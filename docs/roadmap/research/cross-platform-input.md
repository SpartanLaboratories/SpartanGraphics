# Cross-platform input: how Phase 1's keys, pointer and scroll should grow

## 1. Question

How should SpartanGraphics' abstract input grow from Phase 1 (keys, pointer, scroll) to cover touch and gestures, text input with IME and clipboard, and custom cursor images, across GLFW desktop, Android and web? It must leave room for gamepad, and SpartanUI and games must be able to build on it.

## 2. Bottom line

- **One pointer model, shaped like W3C Pointer Events, from 0.1.0.** Every pointer event carries `pointerId`, `kind` (mouse, touch, pen, with an open "unknown"), a phase that includes **Cancel**, `isPrimary`, pressure and a modifier snapshot. The mouse is just pointer 0 and is primary. Touch contact reports as `PointerButton.Primary`. This costs nothing on desktop and makes Android and web additive. The same holds for scroll: delta, unit and a precise flag.
- **Deliver events as a queue the backend fills and the game drains once per frame, on the frame thread.** No `Flow` in the contract, and no callbacks fired from foreign threads. libGDX does exactly this. Backends that receive input off-thread (Android UI thread) enqueue and hand over at frame start. "Held keys" and "pointer positions" are derived in common code from the event stream, not asked of the backend.
- **Settle what `Key.A` means before 0.1.0 ships: it is the physical key position, named with W3C `KeyboardEvent.code` values, and it is never a GLFW integer.** Every engine that separates the two (winit, Bevy, Flutter, SDL, Godot) uses physical for game controls and logical for shortcuts and labels. Add a separate logical key and a layout-aware key label in 0.2, additively. Key events carry `repeat`, a modifier set, a device id and a timestamp. Focus loss produces synthesized releases.
- **Text input is a session, not a callback, and the contract must be state-mirroring from the start even though desktop doesn't need it.** Desktop (GLFW) can live on char, preedit and commit events. Android's `InputConnection` and the browser need the editor's text, selection and composing range, and they send back edit operations. Design `TextInputSession` with `update(editorState)` and a stream of edit events. Ship it **Experimental** in 0.2 on desktop, and promote it to `@SupportedExtension` / Stable only after the Android and web backends have built against it. Web must use a hidden `<textarea>`; `EditContext` is Chromium-only.
- **Clipboard and cursors are small platform services with asynchronous or fallible semantics baked in.** Clipboard read and write complete asynchronously and return `Result`, because web permissions and the user-activation rule make a synchronous contract impossible. Cursors are "desired cursor this frame": a standard shape, a hotspotted image with a scale, or hidden. Unsupported shapes fall back; they don't throw.
- **Gestures are an opt-in pure-Kotlin recogniser layer over the pointer stream, not part of any backend contract.** It is parameterised, unit-testable with scripted input, and lands Experimental with the Android backend. Gamepad later fits as new events and a `capabilities` set, provided the event hierarchy is **not sealed**, every event has a `deviceId`, and gamepad buttons never go into `Key`.

## 3. Findings

### 3.1 Pointer model

1. **Unified pointer events are the consensus model on the web, and the nearest thing to a standard.** The W3C Pointer Events spec has `pointerId` (implementation-specific values, `-1` reserved), `pointerType` of `mouse`/`pen`/`touch`, `isPrimary` (one primary per type), `pressure` (0..1; 0.5 while active on hardware without pressure), `button`/`buttons` (touch and pen contact map to button 0, the same as the left mouse button), implicit capture for touch, and `pointercancel`. It also has coalesced events (`getCoalescedEvents`) for fine movement history. Tier: **standard**. [W3C Pointer Events 3](https://www.w3.org/TR/pointerevents3/)
2. **Native touch APIs split ids from indices and have a cancel.** Android's `MotionEvent` pointer *index* changes between events; the pointer *ID* is stable for the pointer's life. A gesture ends in `ACTION_UP` or `ACTION_CANCEL`. Tier: **platform documentation**. [Android multi-touch](https://developer.android.com/develop/ui/views/touch-and-input/gestures/multi). winit says the same for touch: finger ids may be reused after `Ended`, there is a `Cancelled` phase (for example on focus loss), and `force` is `None` where unsupported. [winit Touch](https://docs.rs/winit/latest/winit/event/struct.Touch.html)
3. **libGDX is the "mouse is a special case of touch" model.** `touchDown(x, y, pointer, button)`, `touchDragged(x, y, pointer)`, with `mouseMoved` and `scrolled` desktop-only. Touch always reports the left button. The docs warn that devices differ in how they assign and release pointer indices. Tier: **common practice (one mature library)**. [libGDX event handling](https://libgdx.com/wiki/input/event-handling), [libGDX mouse, touch, keyboard](https://libgdx.com/wiki/input/mouse-touch-and-keyboard)
4. **Godot keeps separate event classes** (`InputEventScreenTouch`/`ScreenDrag` mobile-only, `InputEventMouseButton`/`MouseMotion`), plus `InputEventMagnifyGesture` and `InputEventPanGesture` as events. Events propagate `_input` then GUI then unhandled, with explicit "handled" consumption. Tier: **common practice**. [Godot InputEvent](https://docs.godotengine.org/en/stable/tutorials/inputs/inputevent.html). Compose has `PointerEvent` with a list of `PointerInputChange`, each with an id, a type (touch, mouse, stylus, eraser), pressure and a consumed flag. I recalled the field list from general knowledge; the docs page did not fetch. Tier: **unverified detail**.
5. **GLFW has no touch events at all.** The input guide doesn't mention touch. On desktop, touch screens arrive as OS-emulated mouse. Tier: **platform documentation (by absence)**. [GLFW input guide](https://www.glfw.org/docs/latest/input_guide.html). GLFW 3.5 adds an opt-in `GLFW_UNLIMITED_MOUSE_BUTTONS` mode, so button ids must not be limited to three. [GLFW 3.5 news](https://www.glfw.org/docs/3.5/news.html)
6. **Gesture recognition is conventionally a separate, opt-in layer over raw pointers.** libGDX ships `GestureDetector` as an `InputProcessor` wrapper with `tap(count)`, `longPress`, `pan`, `panStop`, `fling`, `zoom`, `pinch`, `pinchStop`, with tunable slop and timing, returning consumed or not. [libGDX gestures](https://libgdx.com/wiki/input/gesture-detection). Tier: **common practice**. I did not research Compose's `detectTapGestures`/`detectTransformGestures` or KorGE beyond recalling that they are also library helpers above raw pointer input. Tier: **unverified**.

### 3.2 Keyboard: physical versus logical

1. **Every mature engine that handles both exposes both.**
   - winit: `physical_key` (layout-independent position), `logical_key` (meaning), `text`, `location`, `repeat`. Its docs say to use physical for game controls and filter `repeat`, `text` for text, and logical for shortcuts, and that keybinds should be user-configurable. [winit KeyEvent](https://docs.rs/winit/latest/winit/event/struct.KeyEvent.html)
   - Bevy: `key_code` (physical), `logical_key`, `text`, `repeat`. [Bevy KeyboardInput](https://docs.rs/bevy/latest/bevy/input/keyboard/struct.KeyboardInput.html)
   - Flutter: `PhysicalKeyboardKey` (USB HID usage; a "location on a QWERTY keyboard") versus `LogicalKeyboardKey`. Repeat is a separate event type, and there is a `synthesized` flag for events generated to resync state. [PhysicalKeyboardKey](https://api.flutter.dev/flutter/services/PhysicalKeyboardKey-class.html), [KeyEvent](https://api.flutter.dev/flutter/services/KeyEvent-class.html)
   - SDL3: `scancode` (physical), `key` (layout-mapped), `mod`, `repeat`, `raw`. [SDL_KeyboardEvent](https://wiki.libsdl.org/SDL3/SDL_KeyboardEvent)
   - Godot: `keycode` (Latin label, for shortcuts), `physical_keycode` (US-QWERTY position, for WASD), `key_label` (for on-screen prompts), `unicode` (for text), `location`, `echo`. [Godot InputEventKey](https://docs.godotengine.org/en/stable/classes/class_inputeventkey.html)
   - Browser: `KeyboardEvent.code` is unaffected by layout and modifiers (`KeyQ` is the A key on AZERTY). MDN uses it for WASD. `key` gives the character. For virtual or accessibility keyboards, `code` is best effort. [MDN KeyboardEvent.code](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/code)

   Tier: **established consensus** (five independent engines plus the web platform).
2. **Android is the odd platform.** From general knowledge (the fetched docs page truncated), `KeyEvent.getKeyCode()` is layout-mapped, and `getScanCode()` is a device-driver code that Android does not promise is portable. So the Android backend can only give a *best-effort* physical key: map the scancode (Linux evdev) or assume QWERTY from the keycode. Tier: **unverified**, listed in Gaps. [Android KeyEvent](https://developer.android.com/reference/android/view/KeyEvent) (page truncated).
3. **GLFW:** the key callback receives `key` (token), `scancode` and `mods`. Tokens are the library's own constants. The guide says scancodes are platform-specific but stable, and `glfwGetKeyName` returns the layout-dependent name of a printable key (which is what a "BEEP (B)" hint needs). `GLFW_MOD_CAPS_LOCK`/`NUM_LOCK` need `GLFW_LOCK_KEY_MODS`. [GLFW input guide](https://www.glfw.org/docs/latest/input_guide.html). I could not re-fetch the passage that says what a token represents (US-position versus layout-mapped). Tier: **unverified**, listed in Gaps.
4. **The monolith discards repeat and stores raw GLFW ints** (`KeyAction.key: Int`, `keysDown: HashSet<Int>`), and has no modifiers. Local evidence: `D:\Documents\Programming\GameGraphics\...\Window.kt` lines 419-432 and 505-525, `ui\KeyAction.kt`. The split plan already names this a defect (line 26 of the split plan).

### 3.3 Text input and IME

1. **GLFW (the pinned LWJGL 3.3.4 / GLFW 3.4):** stock GLFW has only the char callback (Unicode code points from the OS text system). The input guide documents no IME or preedit API. [GLFW input guide](https://www.glfw.org/docs/latest/input_guide.html). Upstream IME support is PR glfw/glfw#2130, **still open, milestone 3.6**, with Win32, macOS, X11 and Wayland implementations. Its API is `glfwSetPreeditCallback`, `glfwSetPreeditCursorRectangle`, `glfwResetPreeditText`, `glfwSetIMEStatusCallback`, a `GLFW_IME` input mode, and a Win32-only candidate-list API. [glfw PR #2130](https://github.com/glfw/glfw/pull/2130). GLFW 3.5 (released as 3.5.1) does not list IME. [GLFW 3.5 news](https://www.glfw.org/docs/3.5/news.html)
2. **Notable local fact: LWJGL 3.3.4's own release notes say "glfw: Added experimental support for IME"**, adding exactly those functions, plus `GLFW_IME`, `GLFW_MANAGE_PREEDIT_CANDIDATE` and `GLFW_X11_ONTHESPOT`. So desktop preedit is *reachable* on the pinned LWJGL version, but through a non-upstream, experimental binding. LWJGL 3.4.3 moves to GLFW 3.5.1; I could not confirm whether the IME patch set survives that. Tier: **primary release notes, one source**. [LWJGL 3.3.4 notes](https://github.com/LWJGL/lwjgl3/releases/tag/3.3.4), [LWJGL releases](https://github.com/LWJGL/lwjgl3/releases), [GLFWPreeditCallback javadoc](https://javadoc.lwjgl.org/org/lwjgl/glfw/GLFWPreeditCallback.html)
3. **The event model that GUI toolkits converge on is `Enabled/Preedit/Commit/Disabled` plus a cursor-area hint.** winit: `Ime::Enabled`, `Preedit(String, Option<(begin, end)>)`, `Commit(String)`, `Disabled`. An empty preedit always precedes a commit, and `set_ime_cursor_area` positions the candidate window. Its preedit cursor offsets are **byte** indices. [winit Ime](https://docs.rs/winit/latest/winit/event/enum.Ime.html). iced models it as `InputMethod::Enabled { cursor: Rectangle, purpose: Normal | Secure | Terminal, preedit }` with the same four events, and can draw the preedit as an overlay when a widget doesn't. [iced input_method.rs](https://docs.iced.rs/src/iced_core/input_method.rs.html). SDL3 has per-window `SDL_StartTextInput`/`StopTextInput`, `SDL_StartTextInputWithProperties` (text type, capitalization), `SDL_SetTextInputArea`, `SDL_ClearComposition`, `SDL_HasScreenKeyboardSupport`. [SDL3 keyboard category](https://wiki.libsdl.org/SDL3/CategoryKeyboard). Tier: **common practice**.
4. **Android and the browser use a different model: the platform queries and edits the editor's text.** Android: a custom `View` returns `true` from `onCheckIsTextEditor()` and an `InputConnection` from `onCreateInputConnection(EditorInfo)`. The IME then calls `commitText`, `setComposingText`, `deleteSurroundingText`, `getTextBeforeCursor`, and the app tells it about changes via `InputMethodManager.updateSelection`/`restartInput`. I got this from a fetch that failed to read the page and fell back to general knowledge, so the API list is **unverified against the primary page**. Compose confirms the shape: `PlatformTextInputModifierNode.establishTextInputSession { startInputMethod(request) }`, where the session is a coroutine-scoped object and a new session cancels the old one. [Compose PlatformTextInputModifierNode](https://developer.android.com/reference/kotlin/androidx/compose/ui/platform/PlatformTextInputModifierNode)
5. **Browser: canvas apps use a hidden editable element.** W3C's EditContext explainer states that this is the established practice and "negatively impacts accessibility and increases complexity, leading to buggy behavior". [EditContext explainer](https://w3c.github.io/editing/docs/EditContext/explainer.html). Zed's GPUI web backend does it ("invisible input element to listen for composition events, since canvases don't receive them"). [GPUI commit](https://git.secluded.site/zed/commit/b9dce952072c26f0415c2da22247ebc326bd30b2). **EditContext** (text, selection, `updateText`, `updateSelection`, `updateControlBounds`/`SelectionBounds`/`CharacterBounds`; `textupdate`, `textformatupdate`, `characterboundsupdate`) is the model-mirroring alternative. [EditContext spec](https://w3c.github.io/edit-context/). Its support is Chromium only (Chrome/Edge 121+, Android Chrome); Firefox and Safari have none, and MDN marks it "Limited availability / not Baseline". [MDN EditContext](https://developer.mozilla.org/docs/Web/API/EditContext), [caniuse](https://caniuse.com/wf-edit-context). Tier: **established** (browser support); the hidden-element practice is **common practice**.
6. **Clipboard.**
   - Web: the async Clipboard API needs a secure context. Reads need transient user activation or a "paste" gesture. Chromium prompts for `clipboard-read`. Firefox and Safari don't support the permissions at all: they require transient activation and show a "Paste" menu that enables after 1 second. It is not available in Web Workers. [MDN Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)
   - GLFW: `glfwGetClipboardString`/`glfwSetClipboardString` are synchronous. I did not verify the string-lifetime and threading notes. Tier: **unverified**.
   - Android `ClipboardManager`: from general knowledge only, not researched.

### 3.4 Custom cursors

1. **GLFW:** `glfwCreateCursor` takes 32-bit little-endian **non-premultiplied RGBA**, rows from the top left, with `xhot`/`yhot`. `glfwCreateStandardCursor` shapes may be unavailable on a platform, in which case it returns `NULL`. Cursor objects are created and destroyed explicitly. [GLFW input guide](https://www.glfw.org/docs/latest/input_guide.html). The guide does not discuss HiDPI scaling of cursor images. Tier: **platform documentation**.
2. **Android:** `PointerIcon.create(Bitmap, hotspotX, hotspotY)` since API 24, the hotspot must lie inside the bitmap, and `null` means the default. `View.setPointerIcon`/`onResolvePointerIcon` set it. A system icon comes from `PointerIcon.getSystemIcon`. It is mouse- and stylus-relevant only. [PointerIcon reference](https://developer.android.com/reference/android/view/PointerIcon.html), [SDL's reflection fallback for API 24](https://skia.googlesource.com/third_party/sdl/+/7b6cc30d14a1ef9254d39664fcff216d69bf1a76%5E%21/). Tier: **platform documentation**.
3. **Web:** CSS `cursor: url(...) x y, <fallback>`. I did not fetch a source for the syntax (it requires a fallback keyword and an image URL, so RGBA must be encoded to PNG or a data URL, and density needs `image-set`). Tier: **unverified**, from general knowledge.

### 3.5 Event delivery and threads

1. **libGDX dispatches events on the render thread just before `ApplicationListener.render()`**, so handlers need no synchronisation. Gesture callbacks do the same. [libGDX event handling](https://libgdx.com/wiki/input/event-handling), [libGDX gestures](https://libgdx.com/wiki/input/gesture-detection). This is the design that fits "each platform owns the frame". Tier: **common practice**.
2. **Android:** the OpenGL ES touch tutorial confirms the renderer runs on a separate thread from the UI thread, touch arrives at `onTouchEvent` on the UI thread, and shared state needs `@Volatile`. [Android OpenGL touch](https://developer.android.com/develop/ui/views/graphics/opengl/touch). `GLSurfaceView.queueEvent(Runnable)` is the usual hand-off, but I couldn't confirm it from a primary page. Tier: **platform documentation** for the thread split; **unverified** for `queueEvent`.
3. **GLFW:** callbacks fire inside `glfwPollEvents()` on the main thread (the monolith relies on this, `Window.kt` lines 200-201 and 414-483). **Web:** a single thread, events fire from the event loop and the frame arrives via `requestAnimationFrame`. Both are easy to queue.
4. **Polling gamepads** is the web model (`navigator.getGamepads()` each frame) and the GLFW model (`glfwGetGamepadState`), so a per-frame drain fits them directly. [MDN Gamepad API](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API/Using_the_Gamepad_API), [GLFW input guide](https://www.glfw.org/docs/latest/input_guide.html)

### 3.6 Gamepad (room only)

- **GLFW:** `glfwJoystickIsGamepad`, `glfwGetGamepadState` filling `buttons[15]` and `axes[6]` in a standard layout (`GLFW_GAMEPAD_BUTTON_A`, `GLFW_GAMEPAD_AXIS_RIGHT_TRIGGER`), with SDL_GameControllerDB mappings updatable at runtime via `glfwUpdateGamepadMappings`. [GLFW input guide](https://www.glfw.org/docs/latest/input_guide.html)
- **Browser:** polled `Gamepad` objects with `mapping == "standard"` when the browser remaps; `buttons[i].value` for analog triggers; `axes` -1..1; `gamepadconnected`/`disconnected` events; `index` may be reused after disconnect; Firefox exposes a gamepad only after the user interacts with it. [MDN Gamepad API](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API/Using_the_Gamepad_API)
- **Android:** `InputDevice` sources and `MotionEvent`/`KeyEvent` button codes. Not researched; **unverified** (general knowledge only).
- **Convergence:** all three expose a "standard gamepad" layout, identify devices by an index that can be reused, and have connect/disconnect. Godot already has distinct `InputEventJoypadMotion`/`JoypadButton` classes. [Godot InputEvent](https://docs.godotengine.org/en/stable/tutorials/inputs/inputevent.html). Tier: **common practice** for the standard-layout idea.

## 5. Pitfalls and regrets

- **Raw GLFW ints in the public key type** (today's `KeyAction.key: Int`). It can't port to web or Android, and it can't be saved in a keymap that survives a backend change. Name keys with stable ids.
- **Dropping key repeat** (the monolith does, `Window.kt` line 428) breaks held Backspace and arrow keys in a text field. Deliver repeats with a flag; let UI decide.
- **Stuck keys and drags on focus loss or Android pause.** GLFW has no cancel event. Flutter and winit both synthesize releases and cancels. The tracker in common code must do the same on a `FocusChanged(false)`.
- **Index versus id confusion for pointers** (Android indices change; web pointer ids and gamepad indices are reused). Expose only stable ids and treat a reused id after Up as a new pointer.
- **Byte offsets in preedit ranges** (winit's choice). Kotlin strings and JS and Android text are UTF-16, so specify UTF-16 code-unit offsets in the contract. This is my reasoning, not a sourced claim.
- **Making EditContext the web design.** It is Chromium only. Hidden-element input is the baseline, and the W3C itself admits it is buggy and hurts accessibility.
- **A synchronous clipboard in the contract.** It can't be implemented on web without breaking on Firefox and Safari, and it forces a breaking change once the web backend lands. Use an asynchronous, `Result`-returning contract from day one, the same reason the draft architecture makes `AssetSource` `suspend`.
- **Sealed event hierarchies.** Adding a subtype (gamepad, pen hover, IME events) after 1.0 breaks every consumer's exhaustive `when`. This is also user-rule consistent: sealed only where the closed set is the contract, and the set of input event kinds is not closed. Likewise avoid `data class` for public events: adding a field later breaks `copy` and `componentN` binary compatibility. (My reasoning, standard Kotlin library practice; the Q3 researcher owns the idiom detail.)
- **Synthesizing mouse events from touch inside the library.** The web spec limits compatibility mouse events to the primary pointer, which makes apps see duplicates. Let consumers choose by `kind`.
- **Pointer hover assumptions in SpartanUI.** Touch has no hover, so ui-core's hover state must key off `kind`.

## 6. Recommendation for this repo

Shapes below are at the level the roadmap needs, not final signatures.

### 6.1 Contract to freeze at 1.0

**Events (graphics-core `.input`).** `InputEvent` is a non-sealed interface (open hierarchy). Every event has `timestamp` and `deviceId`. It is delivered by `InputSource`, which the game drains once per frame on the frame thread.
- `PointerEvent`: `pointerId`, `kind` (open value class), `phase` (Enter, Down, Move, Up, Cancel, Exit), `position` (window-logical coordinates), `button` (open `PointerButton`: Primary/Secondary/Middle/Back/Forward plus an index escape hatch), `buttons` (set), `pressure`, `isPrimary`, `modifiers`. Reserve optional pen fields (tilt, eraser) for later additively.
- `ScrollEvent`: `dx`, `dy`, `unit` (lines or pixels), `precise`, `modifiers`.
- `KeyEvent`: `key: Key` (physical), `isDown`, `repeat`, `modifiers`, plus (from 0.2) a logical key and text. `Key` is an open value class over a stable string id taken from W3C `code` names (`KeyA`, `Digit1`, `ShiftLeft`, `Numpad1`, `ArrowLeft`). Never GLFW ints; backends map in tables. The id is the serialization form for saved keymaps. SpartanUI's key tables bind these.
- `FocusChanged`, `TextInput`/preedit/commit events (0.2).

**Common-code helpers (not backend contracts).** `InputTracker` derives held keys, pointer positions and edge-panning inputs from the stream and synthesizes releases/cancels on focus loss. Frame-level coalescing of consecutive moves from the same pointer is a parameter (the monolith's 60 Hz throttle becomes a default policy).

**Services (graphics-core `.platform`, reached through the backend, discoverable via `capabilities`).**
- `TextInputSession`: `start(request)` / `stop()` / `update(EditorState{text, selection, composing})` / `setCaretRect(rect)`. The request carries purpose (normal, password, number, email, url, multiline), IME action key, capitalisation. Events back: preedit (text, cursor range in UTF-16 units), commit, and edit operations (replace range, delete surrounding, set composing region, set selection) so Android's `InputConnection` and the browser's `beforeinput` map without loss. Desktop treats commit as "replace selection" and ignores `update` except for the caret rectangle. Start/stop also shows and hides the soft keyboard.
- `Clipboard`: asynchronous `readText()` and `writeText()` returning `Result` (denied or empty are expected failures). Text only at 1.0; rich formats can be added as new methods.
- `CursorService`: a "desired cursor" the UI sets each frame: `Standard(shape)` over a CSS/GLFW intersection (arrow, text, crosshair, pointing hand, resize EW/NS/NESW/NWSE, resize-all, not-allowed, wait), `Image(rgba, w, h, hotspot, scale)`, or hidden. Image cursors are resources with an explicit lifetime. An unavailable shape falls back to the arrow (GLFW already returns `NULL` for some; Android's `getSystemIcon` is limited; web needs a fallback keyword); this returns a `Result` rather than throwing. Cursors are a no-op where the primary pointer is touch.
- `InputSource.capabilities`: a set (touch, pen, imePreedit, softKeyboard, clipboardRead, customCursor, hardwareKeyboard, gamepad). Absence replaces exceptions.

**Gesture recogniser (graphics-core `.input.gesture`).** Pure Kotlin over `PointerEvent`; tap(count), long-press, drag/pan, pinch, fling; slop, timing and tap-interval are constructor parameters; the output is gesture events the consumer routes. Not required of backends, which is what makes it testable at Level 4a with scripted pointers (`graphics-test`'s scripted `InputSource`).

### 6.2 Order

1. **0.1.0 (Phase 1).** Land the *shapes* even though only mouse and keyboard exist: pointer events with id, kind, phase including Cancel, primary; scroll with unit and precise; `Key` as physical, W3C-named ids; repeat, modifiers, timestamps, device id, focus; the open event hierarchy; `InputTracker`. These are the pieces expensive to change later. Do not freeze yet (the 0.x rule allows breaks at phase boundaries), but ship the right shape so SpartanUI's key tables (U3) and the game client's edge panning build on stable ids.
2. **0.2 (real fonts + text input, desktop).** `TextInputSession` (Experimental, behind `@RequiresOptIn`), char/preedit/commit via the experimental LWJGL IME binding where it works and char-only otherwise, caret rectangle (needs font metrics, so this ties to the text-rendering track), `Clipboard`, `CursorService` (GLFW standard cursors and `glfwCreateCursor`), logical key and layout-aware key label (`glfwGetKeyName`).
3. **0.3 (Android).** Multi-touch via `MotionEvent` ids, cancel, `InputConnection`-backed `TextInputSession` (the first real test of the state-mirroring shape), soft keyboard show/hide, `ClipboardManager`, `PointerIcon`, hardware-keyboard mapping, and the gesture recogniser (Experimental). The Android sample app is the "real consumer" that justifies graduating the text session and gestures.
4. **0.4 (web).** Pointer Events with `setPointerCapture` and `touch-action: none` on the canvas, hidden-`<textarea>` text input with composition and `beforeinput`, async clipboard, CSS cursors, `KeyboardEvent.code`.
5. **1.0.** Freeze the events, `InputSource`, `TextInputSession`, `Clipboard`, `CursorService`. Backend contracts go to `@SupportedExtension`. The gesture recogniser is not a backend contract, so it can graduate in a 1.x minor.
6. **After 1.0.** Gamepad (standard-layout events produced by the backend's per-frame poll-and-diff: GLFW `glfwGetGamepadState`, web `getGamepads()`, Android `InputDevice`), pen tilt/hover, trackpad gestures, haptics, IME candidate windows, rich clipboard. Each lands as a new event type or a new capability interface.

### 6.3 Reasoning

I would reject two obvious options. First, a `Flow<InputEvent>` contract: it adds a coroutine dependency to a contract that must also work in a plain frame callback, it blurs which frame an event belongs to, and it hides the thread hand-off the backend must do anyway. A queue drained per frame matches libGDX and "each platform owns the frame", and a `Flow` adapter can be a separate extension. Second, a callback-only text API shaped on GLFW's char callback: it works for desktop and then forces a breaking redesign when Android's `InputConnection` needs the editor text. Designing the state-mirroring session now, but keeping it Experimental until Android and web have built against it, honours decision 4 (freeze only after proof) and the user's three-tier rule. Making `Key` physical now is the cheap half of a decision that is expensive later, because saved keymaps and SpartanUI's `Key.B` bindings would otherwise change meaning.

## 7. Gaps

- **Research stopped early: the session limit was hit** before I could re-fetch GLFW's key-input section (what a `GLFW_KEY_*` token represents: US-layout position or layout-mapped) and the clipboard section (string lifetime, threading). Treat "GLFW tokens map to physical" as unverified; the Phase 1 desktop table must be checked against the actual `glfwGetKeyScancode` behaviour.
- **Android primary pages did not parse** (`InputConnection`, `KeyEvent`, `GLSurfaceView`); those API lists come from general knowledge. In particular, I haven't verified that `getScanCode()` can serve as a stable physical key on Android, or that `queueEvent` is the recommended hand-off. The Android physical-key mapping is the weakest part of the keyboard recommendation.
- **Android clipboard, Android gamepad (`InputDevice`), CSS `cursor` syntax and density handling, the Chromium Keyboard Map API (for layout-aware labels on web)** were not researched or sourced.
- **Whether LWJGL's experimental IME bindings work in practice** (on Windows, with the candidate window) and whether they survive in LWJGL 3.4.3 / GLFW 3.5.1 is unverified. This blocks any promise of desktop preedit; the design above avoids depending on it by treating preedit as a capability.
- **Not researched:** KorGE, Bevy touch/pointer, SDL3 touch and pen events, Compose gesture helpers, and Compose Multiplatform's desktop/web text input. The comparison table is thin for those.
- **I did not read GitHub issue #1 or its comments**, only the split plan and the draft architecture. The draft's idea of putting text input, clipboard and cursor shape in `.platform` is consistent with this report, but the decision is the caller's.
- **Soft-keyboard insets** (the keyboard covering the focused field: Android `WindowInsets`, web `visualViewport`) and **safe-area/density handling for cursor images** are reservations I believe the surface contract needs, but I have no sourced evidence in this report; they overlap with the surface and backend-contract researchers.
- Firecrawl was not used (credits are low), so a few issue and PR threads (for example libGDX IME limitations) weren't found.
