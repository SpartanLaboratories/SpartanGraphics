# GPU API per platform, bindings, and shader strategy

Researcher 4 of 12. Date of research: 2026-10-11. Tools: WebSearch and WebFetch only (no Firecrawl). The web tools hit a session limit at the very end, so two follow-up checks (libGDX `CHANGES` for the WebGL2 version, and the Chrome 146 compatibility-mode limits) are marked as unverified in Gaps.

## 1. Question

For the final state (Windows primary; macOS and Linux "should work"; Android; web; a later, unscheduled 3D track), which GPU API should each SpartanGraphics backend target, through which Kotlin, JVM and Wasm bindings, and how should shaders (including the consumer-supplied custom shaders scheduled last) be authored across them?

## 2. Bottom line

- **Target the OpenGL family everywhere through 1.0: GL 3.3 core on desktop (LWJGL), GLES 3.0 on Android, WebGL2 on web.** All three are one API level (WebGL2 is "based on OpenGL ES 3.0"), they cover the stated 10k-sprite target with instancing or merged batches, and they are the only option with mature Kotlin/JVM/JS bindings on all three platforms today. WebGPU on every platform is not viable as the only path in 2026 (section 3.1, 3.2).
- **Web renderer: Kotlin/JS + WebGL2 first; `wasmJs` only if it later proves equal.** Kotlin/Wasm is still Beta, its arrays live in GC memory (every typed-array upload is a copy), and Kool's own README says its Wasm backend "seems to suffer from many JS-interop upcalls" and is "in most cases slower than JS", recommending plain JS. Keep commonMain code free of JS-only APIs so a `wasmJs` variant stays cheap.
- **Android: GLES 3.0 minimum via `GLSurfaceView`, hidden behind the surface contract.** 99.5% of handheld devices (98.2% report GL 3.2) have GLES 3.0 or better. Vulkan is not universal (7.4% of handhelds have none; 62% are only Vulkan 1.1). Reject `GameActivity` (C/C++ oriented) and Swappy (no documented Java/Kotlin API). The lifecycle fact that matters for the contracts: the EGL context, and every GL object in it, can be destroyed at any pause. So every GPU resource must be re-creatable from CPU-side data.
- **Shaders: author once as a GLSL ES 3.00 subset and prefix the `#version` line per platform** (`#version 300 es` plus precision on GLES/WebGL2; `#version 330 core` on desktop). Do this from G5 onward, so Phase 1 does not hard-code `#version 330 core` as the monolith does. Do not adopt WGSL, SPIR-V or a cross-compiler for the built-in shaders. A cross-compile or DSL path (naga, SPIRV-Cross via LWJGL's `lwjgl-spvc`, or a Kool-style Kotlin shader DSL) is the right *later* answer only if a WebGPU backend lands.
- **Custom shaders (Experimental, last): consumers write GLSL ES 3.00 fragment/vertex source against a documented, fixed interface (attribute layout, uniform block, texture units).** The seam should accept a *set of dialect-keyed sources*, so a future WGSL backend can be added without breaking it. Do not promise runtime cross-translation; none of the cross-compilers has a Kotlin or Android/web runtime binding.
- **Leave open, do not build now:** WebGPU as an *additional* backend module (browser WebGPU is shipped everywhere but Linux and Android are partial; the JVM and Android bindings are alpha/beta); macOS Metal/MoltenVK only if Apple removes GL (no removal announced). The one thing to decide before 1.0 is that the backend contracts leak no GL concepts and carry an explicit "GPU resources lost, re-upload" event. The abstraction level itself is question 5's lane.

## 3. Findings

### 3.1 Browser WebGPU availability (late 2026)

- Chrome and Edge: desktop since 113 (Windows D3D12, macOS, ChromeOS). Android since Chrome 121, on Android 12+ with ARM, Qualcomm and Intel GPUs. Imagination GPUs on Android 16+ (Chrome 139). Samsung Xclipse and others are TBD. Linux: Intel Gen12+ (Chrome 144), NVIDIA 535.183.01+ on Wayland (Chrome 147), else behind flags. Windows ARM64 is flag-only. Firefox: Windows since 141; macOS since 145 (macOS 26+), all macOS since 147; Linux only in Nightly; Android off by default (needs `gfx.webgpu.ignore-blocklist`). Safari: 26 on macOS, iOS, iPadOS, visionOS. **Evidence: established consensus** (first-party status pages). Sources: [web.dev, 2025-11-25](https://web.dev/blog/webgpu-supported-major-browsers), [gpuweb Implementation Status wiki](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status).
- Chrome 146 (2026-02-25) adds an opt-in "compatibility mode" that runs WebGPU on OpenGL ES 3.1 on Android (`requestAdapter({featureLevel:"compatibility"})`), which widens WebGPU's reach on older Android hardware. The exact restrictions were not checked (Gaps). **Evidence: one first-party source.** [Chrome blog](https://developer.chrome.com/blog/new-in-webgpu-146).
- Compare WebGL2: about 97.1% global support; Chrome 56, Edge 79, Safari 15, Firefox 51. **Evidence: common practice (caniuse).** [caniuse](https://caniuse.com/webgl2).
- Reading: WebGPU is a fine *optional* web path in late 2026, but "WebGPU only" would still lose Linux browsers on stable Firefox, Firefox Android, and non-listed Android GPUs. Kool ships both and falls back from WebGPU to WebGL. [Kool README](https://github.com/kool-engine/kool). Unity still labels its WebGPU support experimental. [Unity 6.2 manual](https://docs.unity3d.com/6000.2/Documentation/Manual/WebGPU-limitations.html). Godot's web export is WebGL2 (Compatibility renderer) only, because Forward+/Mobile need a low-level API its web build lacks. [Godot 4.3 web export docs](https://docs.godotengine.org/de/4.3/_sources/tutorials/export/exporting_for_web.rst.txt) (a 4.3 page; current-version status not checked).

### 3.2 Native WebGPU bindings from Kotlin/JVM

- **LWJGL has no WebGPU binding.** Requests are open or closed as duplicates: [#614 "wgpu bindings"](https://github.com/LWJGL/lwjgl3/issues/614) (open, 2020), [#944](https://github.com/LWJGL/lwjgl3/issues/944) (closed Dec 2024). LWJGL 3.4.0 added RenderDoc, SDL 3 and libspng bindings, plus a preview FFM-based "Runtime Bindings Generator" that needs JDK 25. [3.4.0 notes](https://newreleases.io/project/github/LWJGL/lwjgl3/release/3.4.0). **Evidence: first-party (issues, release notes).**
- **wgpu4k** (Kotlin Multiplatform, wgpu-native on JVM): version 0.1.1, "Beta"; JVM x64 Windows "first class", Linux/macOS best effort, JVM arm64 Windows not supported; Android work in progress; requires JDK 25+ and Gradle 9.10+. [wgpu4k README](https://github.com/wgpu4k/wgpu4k). Kool's desktop WebGPU path uses it and calls it "mostly working", requiring Java 22 (Project Panama). [Kool README](https://github.com/kool-engine/kool). **Evidence: common practice, young.**
- **jWebGPU** (xpenatan): JNI/Java bindings for wgpu-native and Dawn, plus a wasm artifact; release 0.3.2, 2026-07-18. [Maven listing](https://mvnrepository.com/artifact/com.github.xpenatan.jWebGPU/webgpu-jni). **One source.**
- **androidx.webgpu**: a first-party Kotlin WebGPU API over Dawn; `1.0.0-alpha06` (2026-10-07), min API 26, experimental APIs behind `@ExperimentalWebGpuApi`. [AndroidX release page](https://developer.android.com/jetpack/androidx/releases/webgpu). **Evidence: first-party, alpha.** This is the notable change versus a year ago: an official Android WebGPU Kotlin route now exists, but it is pre-beta.
- Dawn and wgpu expose the shared `webgpu.h` C header so other languages can bind through C FFI. [Chrome ecosystem post](https://developer.chrome.com/blog/webgpu-ecosystem). The Kotlin bindings above all sit on that header, and none is stable. Note the JDK floor: the monolith pins `jvmToolchain(23)`; wgpu4k wants 25+.

### 3.3 Android GL/Vulkan reach

- Google dashboard (data to 2025-11-24, API 23+): handheld GL ES 3.2 = 98.24%, 3.1 = 0.39%, 3.0 = 0.86%, 2.0 = 0.49%. All devices: 3.2 = 94.64%, 3.1 = 2.62%, 3.0 = 0.80%, 2.0 = 1.91%. Vulkan, handheld: none 7.37%, 1.0.3 3.86%, 1.1 62.09%, 1.3 26.01%, 1.4 0.67%. [Android dashboards](https://developer.android.com/about/dashboards). **Evidence: first-party.** A GLES 3.0 floor reaches about 99.5% of handhelds. A Vulkan floor reaches about 92.6% (about 88.8% at Vulkan 1.1+).
- Android's own docs call Vulkan the primary low-level API, and say OpenGL ES remains supported but is no longer under active feature development. Android 15+ ships ANGLE (GLES over Vulkan) as an optional layer. [Android Vulkan overview](https://developer.android.com/games/develop/vulkan/overview). **Evidence: first-party.** Reading: GLES is the safe floor now, but it is a strategic dead end for the *3D* track.

### 3.4 Android surface, frame pacing, lifecycle

- `GameActivity` is a Jetpack library to handle lifecycle, input and text input *in C/C++* (via `native_app_glue`), rendering into a `SurfaceView`. [GameActivity docs](https://developer.android.com/games/agdk/game-activity). The AGDK frame-pacing library (Swappy) documents only native C++ calls; it uses the NDK Choreographer (API 24+), falling back to the Java Choreographer (API 16+). [Frame pacing docs](https://developer.android.com/games/sdk/frame-pacing). **Evidence: first-party.** Neither fits a Kotlin-only library.
- The official `GLSurfaceView.Renderer` docs say the EGL context can be lost (typically on wake from sleep) and all GL resources associated with it are deleted, so the renderer must recreate what it needs. [GLSurfaceView.Renderer](https://developer.android.com/reference/android/opengl/GLSurfaceView.Renderer). `setPreserveEGLContextOnPause(true)` is a `GLSurfaceView`-only shortcut; developer reports show it fails on some devices (Samsung Fold wallpaper case), and a custom `SurfaceView` plus manual EGL loses it entirely (SDL2 thread). [Samsung forum](https://forum.developer.samsung.com/t/fold-live-wallpaper/29497), [SDL forum](https://discourse.libsdl.org/t/android-resets-opengl-context-after-reopening/31151). **Evidence: first-party plus anecdote.**

### 3.5 Kotlin/Wasm versus Kotlin/JS for the web renderer

- Status: `wasmJs` is **Beta** for core KMP and for Compose (as of the 2025-09-10 page; Kotlin 2.4.0, June 2026, made Wasm incremental compilation stable but a source I found did not show a promotion to Stable). Kotlin/JS is Stable. [Kotlin KMP stability](https://kotlinlang.org/docs/multiplatform/supported-platforms.html), [ADT Magazine on 2.4.0](https://adtmag.com/articles/2026/06/24/jetbrains-kotlin-release.aspx). Kotlin/Wasm needs WasmGC browsers: Chrome 119+, Firefox 120+, Safari 18.2+. [Wasm config](https://kotlinlang.org/docs/wasm-configuration.html). **Evidence: first-party.**
- Interop cost: on Wasm, Kotlin number arrays are WasmGC arrays, not linear-memory bytes, so crossing to JS means copying (`Int8Array(...).toByteArray()` copies; `asInt8Array()` is not a view; the internal storage is inaccessible). On Kotlin/JS the Kotlin `ByteArray` *is* an `Int8Array`, so it can be passed without copying. [Slack: wasm memory APIs](https://slack-chats.kotlinlang.org/t/8217177/does-kotlin-wasm-provide-apis-to-deal-with-wasm-memory-impor), [Slack: ByteArray on wasmJs](https://slack-chats.kotlinlang.org/t/33111836/bytearray-on-wasmjs-not-being-able-to-be-used-as-a-parameter). **Evidence: maintainer statements in chat, not formal docs.** A batched renderer uploads one buffer per frame, so a per-frame copy is affordable (about 10k sprites x 4 vertices x 16-20 bytes is under 1 MB), but the WebGL *calls* themselves are JS-boundary crossings either way.
- Practice: Kool, the closest Kotlin renderer, offers both JS and Wasm browser targets and states the Wasm one "seems to suffer from many JS-interop upcalls", is "in most cases slower than JS", and recommends JS. [Kool README](https://github.com/kool-engine/kool). **Evidence: one maintainer's stated experience on a mature Kotlin engine.** JetBrains claims Wasm outperforms JS on Compose workloads (vendor benchmark, not a call-heavy WebGL workload). [Kotlin/Wasm overview](https://kotlinlang.org/docs/wasm-overview.html). The `org.khronos.webgl` types (including `Float32Array`) exist for both JS and Wasm-JS in the stdlib. [Kotlin API docs](https://kotlinlang.org/api/core/kotlin-stdlib/org.khronos.webgl/index.html).
- Threading: not established by any source I found (Gaps).

### 3.6 Shader strategies

- **Shared GLSL dialect.** WebGL2 is based on GLES 3.0 (Mozilla/luma.gl via search), and libGDX's `GL30` interface treats GLES 3.0 as one level that desktop maps onto desktop OpenGL. [libGDX wiki](https://libgdx.com/wiki/graphics/opengl-es-support). Godot's web build uses its OpenGL3 backend as WebGL2. The monolith's six shaders are trivial (`layout(location)` inputs, `uniform vec2/vec4`, `sampler2D`) and port by changing the first line. **Evidence: common practice; the "patch `#version`" mechanics are my reading of the GLSL specs (Gaps).**
- **Cross-compilation exists but not for our runtimes.** naga (wgpu) translates WGSL/SPIR-V to SPIR-V, MSL, HLSL (primary) and GLSL 330+/ES 300+ (secondary support). [naga on docs.rs](https://docs.rs/crate/naga/latest). LWJGL ships `lwjgl-shaderc` and `lwjgl-spvc` (SPIRV-Cross) bindings, version 3.4.3. [lwjgl-spvc](https://central.sonatype.com/artifact/org.lwjgl/lwjgl-spvc/), [lwjgl-shaderc](https://central.sonatype.com/artifact/org.lwjgl/lwjgl-shaderc/). Both are JVM-host tools: usable inside the planned build-time Gradle plugin, not at runtime on Android or the browser. **Evidence: first-party / registry.**
- **Kotlin shader DSL.** Kool writes all shaders in KSL, a Kotlin type-safe builder that generates both GLSL and WGSL. [Kool README](https://github.com/kool-engine/kool). This is the one proven route to "one shader source, GL and WebGPU" in Kotlin, and it needs no runtime compiler on any platform. It is a large investment.
- **C abstractions.** sokol_gfx offers GL core/GLES3/WebGL2/Metal/D3D11/WebGPU(/Vulkan) backends but the shader code must match the selected backend, so a cross-compiler is still needed. [sokol README](https://cdn.jsdelivr.net/gh/floooh/sokol@master/README.md). LWJGL binds bgfx, but bgfx/sokol have no Kotlin/JS or Android Kotlin binding; they would add native glue on two platforms and break a pure-Kotlin web target. (That last clause is inference; see Gaps.)

## 5. Pitfalls and regrets

- **Hard-coding `#version 330 core`** (as the monolith does in `Window.kt` and `UiRenderer.kt`) makes the shaders non-portable to GLES/WebGL2; fix at G5, it is a one-line change then.
- **GL object handles in a shared contract.** GL handles die with the context on Android (and on WebGL `contextlost`); caching them in public types, or treating a texture as "uploaded once", guarantees a black screen after the first backgrounding. The contracts should model uploads as re-playable from retained CPU data (decoded pixels, glyph-atlas recipe).
- **`preserveEGLContextOnPause` is not a lifecycle strategy.** Reports show it failing on some devices; treat it as an optimisation, never the correctness mechanism.
- **Betting on a young binding in a frozen contract.** wgpu4k is 0.1.x, androidx.webgpu is alpha, LWJGL has nothing; anything frozen at 1.0 must not require them. Kool's WebGPU desktop backend forces Java 22; wgpu4k forces JDK 25. A JDK floor leaking into a library's consumers is a public-API cost.
- **Wasm in the hot path.** Kool's experience: upcall-heavy renderers run slower on Wasm than on JS.
- **Apple OpenGL.** Deprecated since macOS 10.14; macOS 26 still ships it (AGL is a no-op, OpenGL itself remains in the SDK) and Apple has made no removal announcement. [macOS 26 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes), [Apple forums](https://developer.apple.com/forums/thread/796543). Kool simply dropped GL on macOS in favour of Vulkan/WebGPU, which is the precedent for how a Kotlin engine escapes it.
- **Chasing a cross-compiler early.** naga's GLSL output is secondary-supported; SPIRV-Cross and shaderc exist only as JVM-host tools here. A build pipeline built around them before a second shader language exists is cost with no consumer.
- **GL is strategically capped.** GLES 3.0 / WebGL2 have no compute and no storage buffers (spec knowledge); luma.gl and Kool's WebGPU-only demos (path tracing, deferred, compute particles) show where the ceiling is. Fine for 2D including the scheduled particles; not fine for a serious 3D track.

## 6. Recommendation for this repo

**Per phase, per backend**

| Phase | Desktop (Win; mac/Linux untested) | Android | Web | Shaders |
|---|---|---|---|---|
| Phase 1 / 0.1.0 | LWJGL 3.3.4, GL 3.3 core, GLFW (as planned) | none | none | Write built-ins as the ES 3.00 subset with a per-platform header; desktop header = `#version 330 core`. |
| Fonts and text input | unchanged API; glyph atlas = dynamic sub-texture updates | none | none | unchanged |
| Android (0.x) | unchanged | **GLES 3.0** via `GLSurfaceView` + `setEGLContextClientVersion(3)`; `uses-feature glEsVersion=0x00030000`; renderer on `onSurfaceCreated` rebuilds all GPU resources | none | header `#version 300 es` + precision |
| Web (0.x) | unchanged | unchanged | **Kotlin/JS (IR) + WebGL2**; commonMain WebGL code kept Wasm-clean | header `#version 300 es` + precision |
| 1.0 | frozen; backend contracts graduate | frozen | frozen | built-in dialect is internal, not frozen |
| Post-1.0 features | upgrade LWJGL to 3.4.x when convenient | GLES 3.0 (raise to 3.1 only if compute is wanted) | optional `wasmJs` artifact once Stable and benchmarked | **Custom shaders (Experimental):** GLSL ES 3.00 source against a documented interface; sources keyed by dialect |
| Unscheduled: 3D track | add Vulkan (LWJGL, + MoltenVK) or WebGPU as a *second backend module*, not a replacement | `androidx.webgpu` or Vulkan, when out of alpha | browser WebGPU | WGSL or a Kool-style DSL then; naga/lwjgl-spvc in the Gradle plugin |

**Structure.** Put the batched GL ES 3.0 renderer in one place, written against a thin internal `Gl` seam (libGDX `GL20/GL30` model), with three implementations: LWJGL, `android.opengl.GLES30`, and `WebGL2RenderingContext`. A batched renderer issues tens of GL calls per frame, so the interface indirection is negligible and the performance-gated code is maintained once. That is an implementation detail beneath the one-artifact-per-backend-family decision, which stays. How to publish the shared piece (hidden source set versus an internal module) is for the architecture step.

**Reasoning.** GL 3.3 / GLES 3.0 / WebGL2 is the only combination with working, stable, first-party-or-mature bindings on all three official platforms, and the 2D feature list (instancing, texture atlases or arrays, render-to-texture, particles) does not need compute. Every alternative either fails a stability test (Wasm Beta, wgpu4k 0.1, androidx.webgpu alpha, no LWJGL WebGPU) or multiplies renderers (Vulkan/Metal/D3D12) or adds native glue incompatible with the web target (bgfx, sokol). Reject "WebGPU everywhere" and reject Vulkan-everywhere, but keep a slot for each.

**Decide before 1.0 (expensive to change afterwards)**
1. Backend contracts carry no GL concepts (no integer GL handles, GL enums, GLSL strings in built-in paths) and include an explicit "GPU resources lost, re-create" signal. This is the same event on Android context loss, WebGL `contextlost`, and WebGPU device-lost, so one contract covers all.
2. Fix the conventions that differ between GL and WebGPU/Metal/D3D/Vulkan *in the API*, not in shaders: clip-space depth range, render-target Y orientation, texture origin. Spec knowledge (Gaps): GL is -1..1 depth and bottom-left texture origin, WebGPU is 0..1 and top-left. Pick app-facing conventions (the 2D API's y-up or y-down, top-left atlas UVs) so a later backend flips internally.
3. Treat the built-in shader dialect as internal; the custom-shader contract stays Experimental and dialect-keyed, so it can add WGSL later without a major.
4. Do not freeze a JDK floor above what you must (JDK 23 today); any WebGPU desktop module is a separate artifact so its JDK 22/25 requirement stays out of core.

**Test hook (for question 7):** because shader sources are plain strings in one dialect, Level 4a tests can validate them offline (a glslang/`glslangValidator` check on each source, or `lwjgl-shaderc` on a JVM host) without a GPU. I did not verify that glslang accepts ES 3.00 sources through shaderc, only that the CLI route is plausible (Gaps).

## 7. Gaps

- **Spec knowledge not re-verified in this session (stated in Recommendation or Pitfalls, weakest evidence):** that GLSL 330 core accepts ES-style precision qualifiers so one source with a prefix works; GLES 3.0/WebGL2 feature set (instancing, UBO, texture arrays, MRT present; compute and SSBO absent); GL versus WebGPU clip-depth and texture-origin conventions; WebGL `webglcontextlost`/`restored` events; that LWJGL has no official Android support (so the Android backend uses the platform's `GLES30`). Question 7 and the planner should confirm against the specs before relying on them.
- **Not checked because the web tools hit a session limit at the end:** libGDX `CHANGES` for the exact version that added WebGL2 to GWT/TeaVM (a single third-party demo says 1.12); the Chrome 146 compatibility-mode restrictions (limits, texture-array and storage-buffer constraints) and its Android availability status.
- **Not found:** any measurement of per-call Kotlin/Wasm versus Kotlin/JS WebGL cost (only Kool's maintainer statement and Kotlin chat threads); Kotlin/Wasm threading limits (SharedArrayBuffer, COOP/COEP) and whether the new `web` shared source set (js + wasmJs) exists as I recall; Skiko's per-platform GPU API; whether KorGE's current WebGL level is 2; WebGPU share-of-devices numbers for Android (one low-authority page said about 60%; I discarded it).
- **Staleness warning:** the Kool README says Chrome is "still the only browser with WebGPU support", which contradicts the shipping status above, so that README is partly stale. Its Wasm-versus-JS advice may be stale too. Confirm with a small benchmark before the web phase starts.
- **Google's GLSurfaceView page fetch was truncated;** the `preserveEGLContextOnPause` details rely on forum reports plus the official `GLSurfaceView.Renderer` statement from search results, not on the full class page.
- **Not in my brief:** the project's Android `minSdk`, the supported JDK floor for consumers, and whether the web artifact must support `wasmJs` consumers (for example Compose Multiplatform wasm apps). The last decides how soon the `wasmJs` artifact is needed.
