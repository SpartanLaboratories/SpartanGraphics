# Shape rendering and antialiasing for R1/R2 on GL 3.3, GLES 3.0 and WebGL2

## 1. Question

How should SpartanGraphics draw and antialias the R1/R2 shapes (wide lines with caps and joins, circles and ellipses, convex and concave polygons, rounded rectangles, linear and radial gradients, 9-slice, outlines that rotate with their shape, elliptical outlines) on GL 3.3 core, GLES 3.0 and WebGL2, and what does the chosen technique demand of the backend contract frozen at 1.0?

**Decision it informs:** D7. Does the 1.0 contract's "one universal pipeline" (textured, vertex-coloured triangles) suffice for R1/R2, or must 1.0 reserve extra pipeline kinds, extra per-vertex attributes (antialiasing or distance parameter, second UV set), gradient support, or an MSAA request? And what order should R1/R2 land in?

## 2. Bottom line

- **The universal pipeline suffices for every R1/R2 shape at acceptable quality, with no new vertex attribute.** The technique is CPU tessellation in common code plus a feathered antialiasing fringe carried in the vertex colour's alpha (option 2: NanoVG, Dear ImGui, Godot's built-in `antialiased`, KorGE). It needs only position, UV, colour, the already-reserved texture slot, and a white texel to sample. Reject reserving an "AA/distance" attribute or a second UV set: nothing in R1/R2 needs them, and a later SDF pipeline carries its own vertex layout.
- **MSAA cannot be the baseline.** WebGL's `antialias` is a hint the browser may ignore; GLES 3.0 has multisampled renderbuffers but no multisample textures (those arrive in 3.1); MSAA does nothing for edges a fragment shader computes. Fringe AA works identically on all three APIs. Offer MSAA as an optional request that, when granted, lets a consumer switch the fringe off (NanoVG documents exactly this). It is additive after 1.0, so it need not be frozen, but a requested-samples field plus a read-only granted-samples capability is cheap, Experimental until Android proves it.
- **The two things the contract must get right are frame structure, not attributes.** (a) The common layer must know framebuffer-pixel scale per layer (camera zoom times surface density), because both the fringe width and the tessellation tolerance are defined in device pixels and must be recomputed when zoom changes. (b) A `RenderFrame` must be able to carry more than one vertex layout, with pipelines created from descriptors that name a layout, so SDF or gradient pipelines can be added later as optional, capability-gated kinds with the tessellated path as the fallback. Both are Stable at 1.0 structurally; every optional kind is Experimental.
- **SDF/analytic primitives (option 3) are a later optimisation, not the foundation.** Skia, Flutter and Bevy UI use them for circles and rounded rectangles, but each pays with extra pipelines, wide vertices (Bevy UI's vertex carries flags, two radius vec4s, a border vec4 and size) and batch breaks; ellipse and uniform-width ellipse strokes are only approximate in the shader. Land them only if the Level 4c gate shows tessellation cost is a problem. Stencil-then-cover (option 4) is not needed for R1/R2: ear clipping handles simple concave polygons, and the shape set excludes holes and self-intersection.
- **Landing order, SpartanUI first:** 9-slice (nine quads, no new machinery), vertex-colour linear gradient on rectangles, then the shared tessellator, fringe filler and stroker with rounded rectangle fill and outline (focus rings); then lines, circles, polygons; R2 (rotating outline, ellipse, elliptical outline) falls out of the same stroker almost for free; radial gradient on arbitrary shapes last.

## 3. Findings

Tiers: **Consensus** = several independent credible sources or a spec. **Practice** = what mature libraries visibly do. **Opinion** = one source's view. Versions and dates are in section 7.

### F1. A feathered fringe built from vertex-colour alpha is the standard way to antialias CPU-tessellated 2D shapes without MSAA. (Practice)
- NanoVG expands fills and strokes with a fringe of `fringeWidth` (1 device pixel) in `nvg__expandFill` / `nvg__expandStroke`; the create flag is documented as geometry AA that "may not be needed when using MSAA" (claim 1).
- Dear ImGui's `AddConvexPolyFilled`, `AddConcavePolyFilled` and `AddPolyline` emit an inner and an outer vertex per point and give the outer ring zero alpha (`col_trans = col & ~IM_COL32_A_MASK`). Fill triangles and fringe triangles are indexed separately, so they do not overlap. The only texture it samples is a white pixel, `TexUvWhitePixel` (claims 4, 5).
- Godot's `antialiased` parameter (`draw_circle`, `draw_polyline`, `StyleBoxFlat`) attaches "half transparent feathers". Its docs call this "the recommended method, as it has a lower performance impact in most cases", and say MSAA is the fallback for nodes without the parameter (claims 9, 10).
- KorGE's `GpuShapeView(shape, antialiased: Boolean = true)` draws a separate antialiasing border strip (`drawAntialiasingBorder`) (claim 22).
- The consequence for the contract: the fringe lives in the vertex colour, so the universal pipeline already carries it.

### F2. The fringe is defined in device pixels, so tessellation must happen at known pixel scale and be redone when zoom changes. (Practice; strong in source)
- NanoVG transforms path points by the current transform before flattening (the `// transform commands` block of `nvg__appendCommands`), and sets `tessTol = 0.25f / ratio`, `distTol = 0.01f / ratio`, `fringeWidth = 1.0f / ratio` from the device pixel ratio (claim 3).
- Dear ImGui has `_FringeScale`, "scaled by this value, this helps to keep things sharp while zooming at vertex buffer content", and `CircleTessellationMaxError` "(in pixels)" (claim 6).
- Godot divides its feather by the 2D oversampling factor "so that antialiasing doesn't become blurry at viewport resolutions higher than the default" (claim 11).
- PixiJS v8 does the opposite for curves: it tessellates once in local space, caches the geometry in a shareable `GraphicsContext`, and picks the circle segment count from the radius alone ("maximum absolute deviation ... approximately 0.029", in local units). Scale it up and the facets grow. This is the right trade for Pixi (cheap, MSAA hides edges) and the wrong one for a 0.1x to several-x world layer (claim 14).
- Arithmetic (mine, not a source): a circle of radius r px with tolerance t px needs about pi / acos(1 - t/r) segments. At t = 0.25: r = 10 gives about 14, r = 100 gives about 44, r = 1000 gives about 140. Vertex counts are small. Even filled with a fringe (2 vertices per segment) a 100 px circle is about 90 vertices and about 400 indices.

### F3. Sub-pixel and thin strokes need coverage emulation, or they shimmer and vanish at low zoom. (Practice)
- NanoVG's `nvgStroke`: "If the stroke width is less than pixel size, use alpha to emulate coverage. Since coverage is area, scale by alpha*alpha." and clamps the width to the fringe width (claim 2).
- Dear ImGui treats thickness below 1 as 1 and uses a baked-line texture only for integer widths, which requires bilinear filtering (claim 7).
- This matters here because the world layer zooms to 0.1x: a 2-unit-wide ability ring becomes 0.2 px.

### F4. Wide lines cannot be left to the GPU; every comparable library triangulates them. (Consensus for ES; Practice for desktop)
- GLES: "Only width 1 is guaranteed to be supported; others depend on the implementation." (claim 15). Desktop core: wide lines are a deprecated feature removed in forward-compatible core contexts (Khronos forum pointer to GL 3.3 spec E.2.1; the spec text itself was not fetched, see Gaps).
- libGDX `ShapeRenderer.rectLine`, PixiJS `buildLine` (cap `round`/`square`, join `miter`/`bevel`/`round`, `miterLimit`), raylib `DrawLineEx`, and NanoVG `nvg__expandStroke` (cap and join variants, `miterLimit`) all build quads on the CPU.
- The alternative is instanced segment quads with the width expanded in the vertex shader (Bevy gizmos, `lines.wesl`, "algorithm based on https://wwwtyro.net/2019/11/18/instanced-lines.html"). It needs instancing and a second pipeline, so it is not universal-pipeline-compatible.

### F5. Shapes batch with sprites through a white texel (or equivalent) in the same pipeline. (Practice)
- Dear ImGui: `TexUvWhitePixel`. raylib: `SetShapesTexture(texture, source)`, documented as "allowing to reduce draw calls when combined with a texture-atlas". libGDX ShapeDrawer: "Typically this is a single white pixel so that you can easily colour it, and is best packed into an atlas with your other textures." (claims 5, 18, 19).
- This is exactly the repo's "universal pipeline", so the claim holds. The obligation is that the common layer keeps a white texel in every texture a batch can bind, or uses the reserved per-vertex texture slot to bind a shared white texture alongside the atlas.

### F6. MSAA is widely used as the only AA, but it is unreliable as a portable baseline and blind to shader-computed edges. (Consensus on the limits)
- Used as the sole AA: PixiJS v8 `antialias` (default `false`), Bevy `Msaa::Sample4` (default), Flutter Impeller ("On desktop and mobile 4x MSAA is used for all rendering calls") (claims 12, 16, 20).
- WebGL: `antialias` is "its choice of technique (multisample/supersample) and quality" and can be refused. Skia's CanvasKit disabled it by default because "the WebGL spec does not give us control over the exact sample count or even guarantee that 'antialias' means MSAA" (claims 23, 24).
- GLES 3.0: multisampled renderbuffers exist; `glTexStorage2DMultisample` is supported from 3.1, not 3.0. A multisampled offscreen target on 3.0 needs a renderbuffer plus `glBlitFramebuffer` resolve (claim 25). The `EXT_multisampled_render_to_texture` extension is the tile-GPU shortcut; I did not verify its availability on target devices.
- Cost: on tile-based GPUs the multisampled attachment can stay in tile memory (the Khronos Vulkan sample measured "3% bandwidth increase" on one Mali-G76; Vulkan, not GLES, one device). On immediate-mode GPUs the multisampled surface is real memory (claim 26).
- Blind spots: Godot's docs list what 2D MSAA "will not affect": aliasing within nearest-filtered textures, custom 2D shaders, font rendering (claim 10). Four samples give five coverage levels (arithmetic), against 256 from a fringe.
- Skia keeps analytic coverage AA for rounded rectangles "even if the RT is MSAA" (claim 27).

### F7. Analytic/SDF primitives win on quality and vertex count for circles and rounded rectangles, at the price of pipeline and batch complexity. (Practice)
- Skia Ganesh `FillRRectOp` uses a coverage ramp computed in the fragment shader (claim 27). Skia Graphite has a dedicated `AnalyticRRectRenderStep` (claim 28). Flutter draws "standard primitive shapes" with SDFs by default on desktop, and on mobile makes it opt-in "because SDF rendering puts more demand on the GPU" (claim 21). Bevy UI's `ui.wesl` draws rounded boxes and borders from an SDF (claim 17).
- Bevy UI's costs: three separate pipelines (`ui`, `ui_texture_slice`, `gradient`), and a vertex that carries `flags`, `radius_x`, `radius_y`, `border`, `size` and `point` besides position, UV and colour. Bevy also notes "Using the fwidth(distance) was causing artifacts, so just use the distance." Its ellipse distance is a Taubin approximation (`distance_to_ellipse_approx`) (claim 17).
- Consequence for R2: a uniform-width elliptical outline is exactly the case where an SDF approximation is weakest, whereas flatten-and-stroke is exact up to flattening tolerance.

### F8. Concave fills: ear clipping on the CPU is the common choice in UI-scale renderers; stencil-then-cover is the choice in vector-graphics engines. (Practice)
- Ear clipping: ImGui `AddConcavePolyFilled` ("O(N^2) complexity", simple polygons only, with its fringe), PixiJS `buildPolygon` via `triangulateWithHoles` (earcut). Earcut "does not guarantee a correct triangulation on arbitrary input", assumes "rings that don't self-cross or overlap", and its output has T-junctions that are "harmless for rendering" (claims 8, 29).
- Stencil-then-cover: NanoVG `glnvg__fill` (`GL_INCR_WRAP`/`GL_DECR_WRAP` pass, then cover), KorGE (`requireStencil` is `!this.isConvex` for fills), Skia Graphite (stencil renderers; the `kTessellation` path "requires MSAA") (claims 13, 22, 28).
- Stencil also removes double blending on overlapping strokes: NanoVG `NVG_STENCIL_STROKES` makes "path overlaps ... drawn just once" (claim 1).
- For R1 the polygon is a closed shape with no holes (ability cones, regions). Ear clipping is enough, and it keeps stencil out of the contract.

### F9. Gradients have four implementations; the cheap ones are exact for the common cases. (Practice for the implementations; the exactness argument is mine)
- Vertex colours: Dear ImGui `AddRectFilledMultiColor`, libGDX `ShapeRenderer.rect(x, y, w, h, col1, col2, col3, col4)`.
- Ramp/bitmap texture: PixiJS `FillGradient` "creates a texture of the gradient then applies a transform to it", and "Due to GPU interpolation, gradient textures can be relatively small!" (claim 14).
- Shader parameters: NanoVG paint uniforms (box gradient `sdroundrect` in `nanovg_gl.h`), Bevy `gradient.wesl` (linear, radial, conic), Skia shaders.
- Why vertex colours suffice (mine): a linear gradient's parameter t is an affine function of position, so per-vertex colours interpolated across a triangle reproduce it exactly for two stops; extra stops need geometry split at the stop lines. A radial gradient on a circle or ellipse drawn as a fan from the centre is exact along every ray, with only the flattening error (about 0.5% at 32 segments; arithmetic). A radial gradient on an arbitrary shape is not expressible that way and needs a baked 2D texture (Pixi's route) or a shader.
- Texture-based gradients cost a texture binding. Bilinear bleed makes a ramp inside a shared atlas unreliable, so the ramp wants its own texture or padded rows.

### F10. 9-slice is nine quads in a 4x4 vertex grid in CPU-batched renderers; a single quad plus shader in GPU-parameter renderers. (Practice)
- libGDX `NinePatch`: `private float[] vertices = new float[9 * 4 * 5];`. PixiJS `NineSliceGeometry extends PlaneGeometry`, whose `trim` option exists so "transparent padding in the atlas does not bleed into the rendered corners/edges" (claim 14).
- Godot's canvas renderer treats nine-patch as one instance with a `USE_NINEPATCH` shader variant (`SHADER_VARIANT_NINEPATCH`); Bevy has a separate `ui_texture_slice` pipeline (claims 10, 17).
- For this repo, nine quads share the universal pipeline and the existing texture source rectangle. The costs are seam avoidance (share the 4x4 grid vertices) and atlas bleed (extrusion or half-texel inset, an asset-pipeline concern).

### F11. Consumers expect stroke-and-fill with cap, join and miter limit, and gradients as a paint. (Practice)
- Jetpack Compose (androidx main): `class Stroke(width = 0.0f, miter = DefaultMiter, cap = DefaultCap, join = DefaultJoin, pathEffect = null) : DrawStyle()`, `Stroke.HairlineWidth` "Width to indicate a hairline stroke of 1 pixel", and `Brush` gradients through factory functions whose implementations (`LinearGradient`, `RadialGradient`) have `internal constructor`s (claim 30).
- The same shape exists in HTML canvas and SVG (`lineCap`, `lineJoin`, `miterLimit`); I did not fetch those specs.

## 5. Pitfalls and regrets

1. **Caching tessellation across zoom.** Pixi-style local-space caching gives facets at high zoom and a wrong fringe width. ImGui needs `_FringeScale` to patch exactly this. Key any cache on (shape, pixel scale) and rebuild on zoom change; with shapes in the hundreds this is cheap (F2 arithmetic).
2. **Magic feather widths.** Godot's `FEATHER_SIZE = 1.25f` is "empirically determined", with a width-compensation function so lines do not look too soft. Expect to tune; keep the fringe width and tessellation tolerance as a small config object, not constants.
3. **Fringe and translucent overlap.** A translucent stroke whose segments or joins overlap double-blends. NanoVG added a stencil mode for it. With standard quad-strip strokers overlap occurs only where segments are shorter than the stroke width; document it. Do not add stencil to fix it before a consumer hits it.
4. **Winding.** ImGui requires clockwise input because "The anti-aliasing fringe depends on it". The polygon factory must normalise winding, not leave it to callers.
5. **Concave fringe on thin features.** Per-vertex normal offsets (ImGui's method) self-intersect on features thinner than the fringe. Acceptable at 1 px; mention it in the polygon KDoc.
6. **Triangulator robustness.** Earcut gives acceptable results on valid input and garbage on self-intersecting input. Validate and return `Result.failure` instead of passing bad input through.
7. **MSAA assumptions.** WebGL2 `antialias: true` is a request; Skia's CanvasKit team turned it off by default because it broke their coverage-AA assumptions. Fringe plus MSAA is fine (fringe is just wider than needed), but never write code that needs MSAA to look right.
8. **SDF anti-aliasing width.** Bevy found `fwidth` produced artifacts; SDF pipelines need a pixel-scale-aware width, i.e. the same per-layer scale knowledge that F2 requires.
9. **Atlas bleed and seams.** 9-slice cracks at fractional positions if the nine quads do not share vertices, and bleeds if sampled up to the atlas edge (Pixi added trim clamping).
10. **A pipeline per shape kind.** Bevy UI ended with three UI pipelines; each switch breaks a batch. If SDF pipelines are added, expect more draw calls and make the Level 4c gate count them.

## 6. Recommendation for this repo

### Technique per shape (all in common code, in framebuffer-pixel space, into the universal pipeline)

| Shape | Technique |
|---|---|
| Rounded rectangle, fill | Flatten the four corner arcs (tolerance in px), fan or strip from the centre, fringe ring. |
| Any outline, including focus rings | One stroker over a flattened closed path: butt/square/round caps, miter (with limit)/bevel/round joins, fringe on both edges. Transform the path first, so "outline rotates with the object" and "elliptical outline" are the same code path as the axis-aligned rectangle. |
| Line | Open path through the same stroker. Coverage emulation (alpha squared) below 1 px. |
| Circle, ellipse | Parametric flatten, segment count from the larger radius in px (ImGui is "a bit pessimistic" about the same thing), fan plus fringe. |
| Polygon | Validate (3+ points, simple), normalise winding; convex: fan; concave: ear clipping. No holes, no self-intersection in v1 (matches ImGui's stated limit). |
| Linear gradient | Per-vertex colours from t; split geometry at interior stops. Exact. |
| Radial gradient | On circle and ellipse: fan with centre and rim colours, rings for extra stops. On other shapes: not in the first cut. |
| 9-slice | 4x4 shared-vertex grid (nine quads) with the existing texture source rectangle. |

### What the 1.0 contract must reserve

| Item | Status at 1.0 | Why |
|---|---|---|
| Universal vertex layout: position (z reserved), UV, 8-bit RGBA colour, texture slot | **Stable** | Carries fringe (alpha), vertex-colour gradients, every tessellated shape and the white-texel batching trick. No extra attribute. |
| Framebuffer pixel size and density visible to common code per layer (so pixels-per-unit is computable) | **Stable** | Fringe and tessellation tolerance are device-pixel quantities (F2). The Surface SPI in backend-contract-design 6.2 already lists pixel size and density; confirm it stays in the frozen set. |
| `RenderFrame` carries more than one vertex buffer/layout; a `DrawBatch` names the buffer; `PipelineDescriptor` names its vertex layout | **Stable** structure | Makes optional SDF/gradient pipelines additive. This is the one place the universal-pipeline wording in backend-contract-design 6.1 is too tight: "a vertex array slice" per pass would force a contract change later. |
| `createPipeline(desc): Result<...>` with failure meaning "unsupported, fall back to tessellation"; built-in pipeline kinds as an open key set where only `Universal` is mandatory | **Stable** mechanism; each non-universal kind **Experimental** | Capability-gating with a fallback, as the brief requires. Avoids shader source in the descriptor for built-in kinds (shader-language strategy is another researcher's topic). |
| Blend in the descriptor, premultiplied-alpha supported | **Stable** | Gradients with transparent stops and fringe interpolate correctly in premultiplied form (my judgment; straight alpha also works for the ImGui-style fringe). |
| Surface/target config: requested MSAA samples, plus a read-only granted-samples capability | **Experimental** | Additive later, so not required for D7. Reserve only if cheap. Web needs it at context creation, which the platform factory already takes. |
| Stencil state in `PipelineDescriptor` | **Experimental**, already motivated by the visibility mask and rounded-corner clipping | Not needed by R1/R2. Scissor cannot clip to a rounded rectangle, so a SpartanUI rounded clipping group will need it, but that is not R1/R2. |
| Gradient ramp texture format, 2D-baked gradient textures | **Not reserved** | Texture creation from pixels already covers it. |

**Not needed:** an AA or distance attribute, a second UV set (costs 8 of roughly 24 bytes per vertex, about 320 KB per frame at 10k sprites; my arithmetic), instancing, geometry shaders, multi-attachment passes, stencil for strokes, MSAA at 1.0.

### Landing order inside R1/R2 (SpartanUI first)
1. **9-slice**, plus 4-corner/2-stop vertex-colour gradient on rectangles. No tessellator needed.
2. **Tessellation core**: pixel-space flattening, fringe filler, stroker. Ship it with **rounded rectangle fill and outline** (SpartanUI panels, buttons, focus rings on rounded controls).
3. **Lines, circles, polygons** (game targeting indicators). Convex first, then concave via ear clipping.
4. **R2 outline work**: rotating outline and ellipse/elliptical outline are small additions once the stroker exists. Consider releasing them with step 3 rather than as a separate phase; the roadmap can still list R2 as an API deliverable.
5. **Radial gradient on circle/ellipse**, then multi-stop, then radial on arbitrary shapes (needs a baked texture or an optional pipeline).
6. **Only if the 4c gate says so**: optional SDF pipelines for circle and rounded rectangle, behind capability keys.

### Kotlin shape of the API (judgment, from F11 and the repo's rules)
- `abstract class Shape internal constructor()` for the closed-but-growing set. The Compose precedent for paint is `LinearGradient internal constructor(...)` behind factory functions returning the abstract `Brush`, so adding `RadialGradient` is additive. Mirror that with an `abstract class Paint internal constructor()` and factories, not a `sealed` hierarchy that forces exhaustive `when` on consumers.
- Stroke parameters as one final class (`width`, `cap`, `join`, `miterLimit`) built with defaults the way the contract researcher recommends for frozen descriptors (builder, not `data class`), because a constructor with default arguments is not binary-stable when a parameter is added.
- Polygon and gradient factories return `Result` (fewer than 3 points, self-intersection, empty stops). That is an expected failure by the repo's rule.
- Fringe width, tessellation tolerance and minimum line width as one small config object with the quoted defaults (0.5 px per side, 0.25 px, 1 px), not constants.

### Reasoning
The universal pipeline already carries everything a feathered fringe needs, and the fringe is the only AA technique that behaves identically on desktop GL, GLES 3.0 tilers and WebGL2, where MSAA is either a hint or a memory cost. Tessellation in common code keeps the whole R1/R2 feature set testable without a GPU (vertex output can be golden-tested with a tiny software rasteriser in `graphics-test`; my suggestion, not sourced) and keeps the backend obligation unchanged after 1.0. I reject the obvious "reserve an AA/distance attribute and a second UV set now" option: no source I read needs them for tessellated shapes, and the SDF libraries that do need them (Bevy, Skia) use separate pipelines with their own vertex layouts, which the multi-layout frame structure above already admits. I also reject MSAA-first (Pixi, Bevy, Impeller) as the default because of the WebGL2 and GLES 3.0 behaviours in F6.

## 7. Load-bearing claims

Quotes are verbatim from the file, page or commit named. Where a fetch tool summarised a page, I say so. All GitHub files were read through `gh api ... contents/<path>?ref=<pin>`.

1. **NanoVG create flags.** `memononen/nanovg` @ `ce3bf745eb2d2dbc14a50bf2446783f691ac4353` (2026-02-19), `src/nanovg_gl.h`, `enum NVGcreateFlags`: "Flag indicating if geometry based anti-aliasing is used (may not be needed when using MSAA)." and "Flag indicating if strokes should be drawn using stencil buffer. The rendering will be a little slower, but path overlaps (i.e. self-intersecting or sharp turns) will be drawn just once."
2. **NanoVG thin strokes.** Same commit, `src/nanovg.c`, `nvgStroke`: "If the stroke width is less than pixel size, use alpha to emulate coverage. Since coverage is area, scale by alpha*alpha."
3. **NanoVG tessellates in device space.** Same commit, `src/nanovg.c`, `nvg__setDevicePixelRatio`: "ctx->tessTol = 0.25f / ratio; ctx->distTol = 0.01f / ratio; ctx->fringeWidth = 1.0f / ratio;". And `nvg__appendCommands`: "// transform commands" followed by `nvgTransformPoint(&vals[i+1],&vals[i+2], state->xform, vals[i+1],vals[i+2]);` for MOVETO/LINETO/BEZIERTO. Fragment shader `strokeMask`: "Stroke - from [0..1] to clipped pyramid, where the slope is 1px."
4. **ImGui fringe via alpha.** `ocornut/imgui` v1.92.9b (2026-07-31), `imgui_draw.cpp`, `ImDrawList::AddConvexPolyFilled`: "Filled shapes must always use clockwise winding order. ## 8. Gaps

- **No measurements.** I found no published numbers for CPU tessellation cost per shape or for fringe versus MSAA fragment cost on GLES 3.0 phones or WebGL2. The vertex-count figures above are my arithmetic. A synthetic 4c scene (hundreds of rounded rectangles, tens of circles and polylines, plus 10k sprites) should measure tessellation time and draw calls before anyone adds SDF pipelines. **Does not block D7**: the recommendation reserves nothing that depends on those numbers.
- **Desktop wide-line removal not read from the spec.** I have only a Khronos forum pointer to GL 3.3 spec section E.2.1 ("wide lines are disabled in forward-compatible contexts", paraphrased); the PDF text could not be extracted. Not load-bearing: the ES refpage alone justifies CPU stroking.
- **GLES 3.0 multisampled renderbuffers and `EXT_multisampled_render_to_texture`** rest on search-result summaries of Imagination's extension docs, not a raw read of the ES 3.0 spec or the extension text. I did not check which target Android devices expose the extension, nor how Android's `EGLConfig` selection for a multisampled window surface behaves.
- **MSAA cost evidence is Vulkan on one device.** No GLES-specific cost source was found.
- **KorGE is a weaker precedent.** The read was at a branch head, not a release tag, and I did not read its stroker, its gradient shader, or the project's current maintenance state.
- **Skia analytic AA for ovals/lines** I confirmed through file names and `FillRRectOp`; I did not read `GrOvalOpFactory.cpp` itself.
- **Vertex-colour and fan-based gradient exactness, the premultiplied-alpha preference, "no stencil needed for R1/R2", the byte arithmetic and the software-rasteriser test idea are my analysis**, not sourced. The arithmetic is simple; the premultiplied preference is the one to double-check.
- **Not covered:** text antialiasing (the text researcher's lane); sprite-edge antialiasing for rotated sprites (atlas extrusion and padding, asset-pipeline lane); the shader language strategy for optional SDF pipelines (GPU-API researcher); rounded-corner clipping of child content (scissor cannot do it; stencil or an SDF clip would, and no consumer has asked yet).
- **HTML canvas/SVG stroke defaults** (`lineCap`, `lineJoin`, `miterLimit`) are cited from memory in F11 and were not fetched. Compose's `Stroke` is the sourced evidence.
- **Firecrawl was not used** (credits low, as instructed). `WebSearch`, `WebFetch` and `gh api` sufficed; fetch-tool summaries are flagged where they stand in for a raw read.
