# Web compilation target: Kotlin/JS or Kotlin/Wasm, and what a 1.0 contract can promise on klib targets

Researcher N1, 2026-10-11. Informs **D2** (web compilation target and G1's compile-check target) and **D5** (the 1.0 binary-compatibility promise off the JVM).

## 1. Question

As of October 2026, should `graphics-web` / `audio-web` / the web `AssetSource` target Kotlin/JS (IR), Kotlin/Wasm (`wasmJs`), or both through the shared `web` source set, which non-JVM target should G1 add as the compile check, and what binary-compatibility guarantee can a 1.0-frozen KMP contract give on klib targets (JS, Wasm)?

Versions this report is pinned to (all read 2026-10-11): Kotlin 2.4.21 is current (released 2026-10-08), 2.4.20 on 2026-09-07, 2.5.0-Beta1 on 2026-09-23 (`gh release list --repo JetBrains/kotlin`). Doc sources are `JetBrains/kotlin-multiplatform-dev-docs` @ `a357693`, `JetBrains/kotlin-web-site` @ `38512ff`. Code sources are `JetBrains/kotlin` tag `v2.4.20`, `Kotlin/kotlinx-browser` @ `9a2f01f`, `kool-engine/kool` @ `7c95ee9`, `JetBrains/kotlin-wrappers` tag `2026.10.0`.

## 2. Bottom line

- **D2: ship the web backend on Kotlin/JS (IR) first, and make `js` G1's compile-check target.** Kotlin/JS is Stable; Kotlin/Wasm is still Beta in Kotlin 2.4.20 and the Kotlin roadmap (Aug 2026) only lists "Promote Kotlin/Wasm to Stable" as an item in focus, with the next roadmap update in Feb 2027. Both coroutines 1.11.0 and kotlin-logging 8.0.4 publish `js` and `wasmJs` variants, so the dependency criterion does not discriminate.
- **The upload-heavy path is what decides it.** On JS a `FloatArray` *is* a `Float32Array` and `toFloat32Array()` is an `unsafeCast` (zero copy). On `wasmJs` the same function in kotlinx-browser is an element-by-element loop of interop writes. Kool, the closest Kotlin renderer, ships both targets, hand-writes its WebGL2 externals twice, and still tells users plain JS is the recommended target. A zero-per-element route on Wasm exists only through experimental linear-memory APIs (`wasmMemory`, new in 2.4.20).
- **Keep `wasmJs` reachable, do not ship it yet.** Write the web code in `webMain` (the shared source set exists since Kotlin 2.2.20) and add `wasmJs` as a compile-only tripwire on `graphics-web` once the web phase starts, so JS-only assumptions are caught before 1.0 freezes anything. Promote it to a tested, published variant when Kotlin/Wasm is Stable and wasmJs passes the same web Level 4c gate as js. That is option (d) with a tripwire, and it can land before or after 1.0 without breaking a consumer, because a new target is an additive variant.
- **Consumer reach is the real cost of (d), and it is bounded.** Compose Multiplatform web apps target `wasmJs` (Beta) and use a `js` fallback build, so a `js`-only library cannot serve their `wasmJs` compilation (inference from variant attributes, not tested). The named consumers (SpartanUI, the game client, the web sample app) are all under your control, so this is not a 1.0 blocker.
- **D5: promise (i) in writing, build the machinery of (ii) anyway.** JetBrains has published no finalized klib binary-compatibility guarantee: its own design doc says the klib guarantees "are not yet finalized", the BCV README calls klib validation "experimental", and the KGP ABI-validation page is labelled experimental. State at 1.0: JVM/Android binary-compatible; JS and Wasm source-compatible with additive-only evolution enforced by klib ABI dumps and a relink fixture. Do not call klib binary compatibility a contractual promise until Kotlin does.
- **The compiler's own tests show where the real cliff is on klibs.** Adding an *abstract* member that an already-compiled implementor does not implement is a known broken case on Native, JS and Wasm (test `addUnimplementedAbstractMethod` is ignored for all three, citing KT-85018). Adding a *default-bodied* member is exercised and passes. That matches the repo's "every new member has a default body" rule, which is therefore the right rule for klib targets too.

## 3. Findings

### F1. Status: Kotlin/Wasm is Beta, Kotlin/JS is Stable, and promotion of Wasm is planned but undated
- Tier: **established** (first-party, current).
- KMP stability page, "Current platform stability levels for the core Kotlin Multiplatform technology": `Web based on Kotlin/Wasm | Beta`, `Web based on Kotlin/JS | Stable`. Same page, Compose Multiplatform table: `Web based on Kotlin/Wasm | Beta` (no Kotlin/JS row). Source: [supported-platforms](https://kotlinlang.org/docs/multiplatform/supported-platforms.html), source file `topics/overview/supported-platforms.md` @ `a357693` (2026-10-10).
- "Current stability of Kotlin components", "Kotlin compiler": `Kotlin/JS | Stable | 1.3.0`, `Kotlin/Wasm | Beta | 2.2.20`. Source: [components-stability](https://kotlinlang.org/docs/components-stability.html), `docs/topics/components-stability.md` @ `38512ff`.
- Kotlin roadmap (page header: last modified August 2026, next update February 2027), "Compiler" row: "Promote Kotlin/Wasm to Stable" ([KT-88663](https://youtrack.jetbrains.com/issue/KT-88663)), flagged new. No release version is given. Source: [roadmap](https://kotlinlang.org/docs/roadmap.html).
- Kotlin 2.4.0 made Wasm incremental compilation Stable but did not promote the target ([what's new 2.4](https://kotlinlang.org/docs/whatsnew24.html), "Kotlin/Wasm"). 2.4.20 kept shipping Wasm behaviour changes that break code, e.g. an error on top-level `require()` in `@JsFun` declarations ([what's new 2.4.20](https://kotlinlang.org/docs/whatsnew2420.html), "Kotlin/Wasm"). That is normal for Beta ("changes are possible", per the stability-level definitions on the KMP stability page).
- Kotlin 2.4.0 also makes partial linkage always on (F11).

### F2. Wasm needs WasmGC browsers
- Tier: **established**.
- Kotlin docs, "Browser versions": Chrome 119+ and Firefox 120+ "Works by default"; Safari/WebKit 18.2+ works, older "Not supported". `wasmJs` uses the *legacy* exception-handling proposal by default. Source: [wasm-configuration](https://kotlinlang.org/docs/wasm-configuration.html), `docs/topics/wasm/wasm-configuration.md` @ `38512ff`.
- Compose Multiplatform "Supported platforms": Web = "Browsers with WasmGC support". Source: `topics/compose/compose-compatibility-and-versioning.md` @ `a357693`.
- A caniuse page for WebAssembly GC reports global usage of 92.57% (fetched 2026-10-11 through a summarising fetcher, so the figure is not a verbatim page quote; see Gaps). The older caniuse `wasm-gc` data file in `Fyrd/caniuse` still shows Safari as unsupported and 76.32%, which contradicts the Kotlin docs, so I treat that file as stale.
- Consequence: a `wasmJs`-only web backend would exclude roughly 1 in 13 browsers (using the 92.57% figure) and any browser older than late 2024. For a library whose official platforms are Windows, Android and web, that is acceptable for an app, awkward for a library.

### F3. The shared `web` source set exists and is designed for library authors
- Tier: **established**.
- Kotlin 2.2.20: "the Kotlin Gradle plugin adds a new shared source set for web (comprising `webMain` and `webTest`) when you use the default hierarchy template." Stated use: "If you're a library author, and you want to add support for both the `js` and `wasmJs` targets, without duplicating code." Source: [what's new 2.2.20](https://kotlinlang.org/docs/whatsnew2220.html), "Shared source set for `js` and `wasmJs` targets".
- It is in the default template as `group("web") { withJs(); withWasmJs() }` in `KotlinHierarchyTemplate` (`v2.4.0`/`v2.4.20`, `libraries/tools/kotlin-gradle-plugin-api/.../KotlinHierarchyTemplate.kt`). Accessing `webMain` with neither target declared fails at configuration time ([KGP API: webMain](https://kotlinlang.org/api/kotlin-gradle-plugin/kotlin-gradle-plugin-api/org.jetbrains.kotlin.gradle.dsl/-kotlin-multiplatform-source-set-conventions/web-main.html)).
- Shared `external` declarations must be written against `JsAny`-compatible types. `JsAny` is `expect` in `common-js-wasmjs` and on JS the actual is `typealias JsAny = Any` (symbols `kotlin.js.JsAny`, files `libraries/stdlib/common-js-wasmjs/src/kotlin/js/JsAny.kt` and `libraries/stdlib/js/src/kotlin/wasmJs/JsAny.kt` @ `v2.4.20`). The release notes' own example shows the JS and Wasm halves differ (`Promise<String>` versus `Promise<JsString>`) and that the shared version uses `JsString`.
- Interop in the shared source set is flagged: `@ExperimentalWasmJsInterop` is a `WARNING`-level opt-in since Kotlin 2.2 ("the behavior of such API may be changed in the future", symbol `kotlin.js.ExperimentalWasmJsInterop`). Kool opts in for `jsMain`, `webMain` and `wasmJsMain` in `kool.lib-conventions.gradle.kts`.
- You cannot share a source set between several JS targets, only `js` + `wasmJs`, and the default hierarchy template must be on ([multiplatform-hierarchy](https://kotlinlang.org/docs/multiplatform/multiplatform-hierarchy.html), "Kotlin doesn't currently support sharing a source set for these combinations: ... Several JS targets").

### F4. Both web dependencies publish both targets
- Tier: **established** (published Gradle module metadata).
- `kotlinx-coroutines-core-1.11.0.module` (2026-05-08) lists variants with platform `js` and `wasm` (wasm target `js` and `wasi`). `kotlin-logging-8.0.4.module` (2026-05-27) lists `jsApiElements-published` and `wasmJsApiElements-published`, among many native targets. Sources: [coroutines module](https://repo1.maven.org/maven2/org/jetbrains/kotlinx/kotlinx-coroutines-core/1.11.0/kotlinx-coroutines-core-1.11.0.module), [kotlin-logging module](https://repo1.maven.org/maven2/io/github/oshai/kotlin-logging/8.0.4/kotlin-logging-8.0.4.module).
- kotlin-logging's own README still calls its multiplatform support "experimental" ([README](https://github.com/oshai/kotlin-logging), "Multiplatform"). That is a caution about the logger, independent of the JS/Wasm choice; I did not verify what it writes to on either target.
- kotlinx-coroutines checks in a klib ABI dump covering both: `kotlinx-coroutines-core/api/kotlinx-coroutines-core.klib.api` (header `Targets: [..., js, ..., wasmJs, wasmWasi, ...]`) @ tag `1.11.0`.
- Net: the split plan's rule "whichever every chosen dependency supports" is satisfied by both `js` and `wasmJs`.

### F5. WebGL2 and DOM declarations: stdlib has WebGL1 only; WebGL2 externals must be written or imported
- Tier: **common practice** for the finding, **my own grep** for the absence claim (method stated).
- The JS stdlib file `libraries/stdlib/js/src/org.w3c/org.khronos.webgl.kt` @ `v2.4.20` declares `WebGLRenderingContext` and `WebGLRenderingContextBase`; I found zero occurrences of `WebGL2` in it, and zero in kotlinx-browser's `idl/org.khronos.webgl.idl` @ `9a2f01f`. Wasm gets its `org.khronos.webgl` types from kotlinx-browser (`src/wasmJsMain/kotlin/org.w3c/org.khronos.webgl.kt`, `actual external open class Float32Array : ArrayBufferView, JsAny`), with `expect` declarations in `src/webMain`. kotlinx-browser's README badge is "Kotlin Alpha" and Maven Central's latest is 0.5.0 (2025-08-13).
- JetBrains' `kotlin-wrappers` module `kotlin-browser` @ `2026.10.0` does ship `web.gl.WebGL2RenderingContext` (with `drawElementsInstanced`, `createVertexArray`, `bindVertexArray`, `vertexAttribDivisor`, `bufferData(target, srcData, usage, srcOffset, length)`) in `src/webMain/generated`, built for js and wasm. It is date-versioned (2026.10.0, badge Kotlin 2.4.21) and generated by Karakum.
- Kool (a Kotlin engine with both targets) keeps its own `WebGL2RenderingContext.kt` in **both** `kool-core/src/jsMain/.../pipeline/backend/gl/` and `.../wasmJsMain/.../pipeline/backend/gl/` @ `7c95ee9`; it did not share them in `webMain`, which suggests the JS and Wasm external signatures drift in practice.
- A batched 2D renderer needs roughly 40 GL entry points (buffers, VAO, program, uniforms, textures, `drawElements`, scissor, blend). That is small enough to hand-write as `internal external` declarations in `webMain`, and keeps a date-versioned wrapper out of a library whose API is frozen at 1.0.

### F6. Typed-array upload: zero-copy on JS, per-element on `wasmJs`
- Tier: **established** (library source at a pinned commit); the performance consequence is my inference and **no measurement exists** (see Gaps).
- kotlinx-browser @ `9a2f01f`, symbol `FloatArray.toFloat32Array()`:
  - `jsMain` (`arrayCopy.js.kt`): `public actual inline fun FloatArray.toFloat32Array(): Float32Array = unsafeCast<Float32Array>()`.
  - `wasmJsMain` (`arrayCopy.wasm.kt`): allocates `Float32Array(this.size)` and then loops `result[index] = this[index]`, i.e. one JS interop call per element.
- Kotlin's Wasm interop page says the same in prose: you "can copy" Kotlin arrays to JS arrays and typed arrays via adapter functions in kotlinx-browser ([wasm-js-interop](https://kotlinlang.org/docs/wasm-js-interop.html), "Array interoperability"). Type correspondence: `Long` maps to JS `BigInt` on Wasm.
- Why it matters here (my arithmetic, vertex layout assumed): 10k sprites x 4 vertices x 4 to 8 four-byte words is 160k to 320k elements per flush. At one bulk upload per frame and 60 fps, a naive Wasm path is roughly 10 to 19 million interop writes per second, against zero per-element calls on JS. The WebGL calls themselves (tens per frame) are crossings on both targets and are not the problem.
- Mitigations on Wasm, all of which cost code that JS does not need:
  - Write vertices into Wasm linear memory with `kotlin.wasm.unsafe.Pointer` inside `withScopedMemoryAllocator`, then create a `Float32Array(memory.buffer, ptr, n)` on the JS side and call `bufferData` once. `wasmMemory: WebAssembly.Memory` is the sanctioned handle, `@ExperimentalWasmJsInterop`, `@SinceKotlin("2.4")` ("Effectively it's 2.4.20"), declared as an opaque `interface Memory : JsAny` (file `libraries/stdlib/wasm/js/src/kotlin/wasm/unsafe/WebAssemblyMemory.kt` @ `v2.4.20`). It has no `buffer` accessor, so you add your own external. The scoped allocator frees on scope exit, so the view must be consumed inside the scope.
  - Or make the CPU-side vertex buffer itself a JS typed array, as Kool does (`GenericBuffer<B: ArrayBufferView>` in `kool-core/src/webMain/.../util/Buffer.web.kt`, with `put` implemented as per-element `buffer[position++] = value`). That removes the bulk copy but turns every vertex write into an interop call on Wasm.
- Neither route is needed on JS. A single `expect`/`actual` seam (`uploadVertices(FloatArray, count)`) isolates the difference, which is also the shape the web phase would need if `wasmJs` is added later.

### F7. Performance evidence: one maintainer says Wasm is slower for upcall-heavy renderers; the only vendor benchmark is Compose
- Tier: **one source's opinion** (Kool README) plus a **vendor claim** (JetBrains).
- Kool README ("JS vs. WASM Performance", file last edited 2026-05-29): "the WASM backend seems to be suffering from the many required JS-interop upcalls to various Web APIs. Therefore, in most cases, the WASM backend is actually slower than the JS backend, and plain JS stays the recommended target for now." Kool's `main` (2026-09-29) builds both `js` and `wasmJs` in `kool.lib-conventions.gradle.kts`, so the advice is held against a current Kotlin toolchain, though the README sentence may predate 2.4.
- JetBrains: "Compose Multiplatform running on Kotlin/Wasm already shows encouraging performance traits. You can see that its execution speed outperforms JavaScript and is approaching that of the JVM" ([wasm-overview](https://kotlinlang.org/docs/wasm-overview.html), "Kotlin/Wasm performance"). That is a UI-framework workload with a self-owned renderer (Skia), not a call-heavy WebGL workload, so it does not contradict Kool.
- I searched for a published Kotlin/JS-versus-Kotlin/Wasm measurement on WebGL or typed-array workloads and found none. `Kotlin/kotlin-wasm-benchmarks` exists but I did not find interop-call numbers in it. This stays a gap; the D2 recommendation is built so that it does not depend on the number.
- Wasm's genuine advantages for this repo are `Long` as native `i64` and a true 32-bit `Float`; on JS `Long` is emulated and `Float` is a JS number ([idiomatic-kotlin.md](idiomatic-kotlin.md) §3.1, one-source evidence there). Kotlin 2.3 added an experimental `-Xes-long-as-bigint` for JS ([what's new 2.3](https://kotlinlang.org/docs/whatsnew23.html), "`BigInt64Array` for `LongArray`"). Avoid `Long` in per-vertex and per-sprite code on JS.

### F8. Consumer reach: Compose web is Wasm-first with a JS fallback; variants do not substitute
- Tier: **established** for the Compose fact; **inference** for the resolution consequence.
- Compose Multiplatform 1.9.0: "The new `composeCompatibilityBrowserDistribution` Gradle task combines Kotlin/JS and Kotlin/Wasm distributions into a single package. This allows Wasm applications to fall back to the JS target when modern Wasm features are not supported by a browser." Source: [what's new in Compose Multiplatform 1.9.0](https://kotlinlang.org/docs/multiplatform/whats-new-compose-190.html), "Unified web distribution". Kotlin 2.2.20 notes make the same point: "modern browsers use `wasmJs` and older ones use `js`".
- So a Compose app that wants the fallback compiles both targets and needs both variants of every dependency. Published variants carry distinct attributes (`org.jetbrains.kotlin.platform.type` = `js` versus `wasm` with `org.jetbrains.kotlin.wasm.target` = `js`; seen in the kotlin-logging and coroutines module files above). A consumer's `wasmJs` compilation therefore cannot take a `js`-only artifact. I did not build a project to confirm the exact Gradle error.
- Latest Compose Multiplatform at the time of writing: 1.12.1 (2026-09-22), 1.13.0-alpha02 (2026-10-06, minimum Kotlin 2.4.20 for js and wasm). Its notes carry a known "memory access out of bounds" Wasm runtime error with a workaround, an example of Beta-grade Wasm rough edges ([releases](https://github.com/JetBrains/compose-multiplatform/releases)).

- Tier: **common practice**.
- Kool v0.19.0 / `main`: browser = JS and Wasm, WebGL2 and WebGPU backends; recommends JS (F7).
- KorGE v6.0.0 (2025-05-16): README: "JS & WASM for the Web". Source tree has `korge-core/src@wasmJs` with `AGOpenglFactoryWasm.kt` @ `v6.0.0`.

### F10. Kotlin's klib compatibility position: not finalized
- Tier: **established** for the quotes, **inference** for what they mean in practice.
- Kotlin's ABI-validator design doc ([KLibSupport.md](https://github.com/Kotlin/binary-compatibility-validator/blob/master/docs/design/KLibSupport.md)): KLibs come "with a binary compatibility guarantees ... (but unlike the JVM, these guarantees are not yet finalized at the time this document was written)".
- BCV README, "Experimental KLib ABI validation support": "The KLib validation support is experimental and is a subject to change (applies to both an API and the ABI dump format)." BCV 0.18.2 is current (2026-09-02).
- KGP built-in validation ([gradle-binary-compatibility-validation](https://kotlinlang.org/docs/gradle-binary-compatibility-validation.html), `docs/topics/gradle/gradle-binary-compatibility-validation.md` @ `38512ff`): page label `experimental-general`; `abiValidation()` needs `@OptIn(ExperimentalAbiValidation::class)`; tasks `checkKotlinAbi`, `updateKotlinAbi`; it dumps and compares all targets and, when a target cannot be built on the host, infers its changes (`keepLocallyUnsupportedTargets`). Kotlin 2.4.0 streamlined the DSL, removed `abiValidation { klib { enabled } }` and renamed `klib.keepUnsupportedTargets` ([compatibility guide 2.4](https://kotlinlang.org/docs/compatibility-guide-24.html), "Remove redundant ABI validation Gradle DSL elements"). Expect the DSL to move again.
- Kotlin API guidelines, "Choose compatible language and API versions": "On other platforms, consumers can use a compiler version the same as the library's configured language version or any later version." On the JVM, one language version back also works. Source: [api-guidelines-backward-compatibility](https://kotlinlang.org/docs/api-guidelines-backward-compatibility.html).
- The klib ABI version itself is bumped on IR-format changes and "aligned with the language version bump" at 2.2.0 to 2.3.0 (`compiler/util-klib/KotlinAbiVersionBumpHistory.md` @ `v2.4.20`, "Bump 2.2.0 -> 2.3.0"). Fake overrides are no longer serialized in klibs since the 1.4.1 to 1.4.2 bump ("Don't serialize fake overrides anymore"), so inherited members of an interface or class are recomputed when klibs are linked.

### F11. What the compiler's own evolution tests show about adding members
- Tier: **common practice** (the compiler's regression tests, not a documented guarantee).
- Partial linkage is always on from Kotlin 2.4.0 for Native, JS and Wasm ("This feature effectively makes compilers treat linkage issues in Kotlin libraries consistently with Kotlin/JVM"; default log level `SILENT`, so problems appear as runtime errors on first use). Source: [what's new 2.4](https://kotlinlang.org/docs/whatsnew24.html), "Consistent partial library linkage across Kotlin compilers".
- Tests live in `compiler/testData/klib/partial-linkage/` @ `v2.4.20`. Each project builds modules at "STEP 0", then rebuilds only some at "STEP 1", and `main` runs against the mix. Cases that matter here:
  - `severalInheritedImplementations`: interface `I` is empty in `lib1` v1 and gains default `foo()` and `bar` in v2; `lib2` (not rebuilt) holds classes implementing `I`. Result in `main`: the old classes inherit the new default (`expectSuccess("I v2") { instance_I_RemovedDefault.foo() }`). Where an old class inherits two interfaces that both gain the same default, the result is a runtime linkage failure ("inherits more than one default implementation"). No `IGNORE_BACKEND` line, so it runs on all klib backends.
  - `evolutionNewFakeOverride`: base class `X` gains `open fun foo(): String = "new member"`, child `Y : X()` is not rebuilt, and new code calls `Y().foo()` successfully.
  - `evolutionAddDefaultImplementations`: abstract interface members gain bodies; an old implementor that overrides them keeps its override.
  - `addUnimplementedAbstractMethod`: abstract class gains an abstract member that an old subclass does not implement. Expected behaviour is the linkage error "Abstract function 'newFun' is not implemented in non-abstract class ...", but the test header reads `IGNORE_BACKEND: NATIVE, JS_IR, JS_IR_ES6, WASM` with `KT-85018` and notes "JS: Runtime crash ... TypeError: this.newFun_..._k$ is not a function" and "WASM: Backend failure: Cannot find class implementation of method". The in-test comment is about the internal-abstract variant; the whole test is ignored on all three klib backends. I could not read KT-85018 (YouTrack did not render).
- My reading (inference): on klib targets the safe additive change is a member *with a default body*; a new abstract member is unsafe, for third-party implementors compiled earlier. I found no test that exactly mirrors "new default-bodied method on a public interface, implementor in a separate pre-compiled klib that implements only that interface" (the closest are `severalInheritedImplementations` and `evolutionNewFakeOverride`), which is why the repo's own fixture (section 6) is still needed.

### F12. How "binary" compatibility works for JS and Wasm
- Tier: **inference** from the above plus how klib-based targets are built; no first-party page states it.
- A JS or Wasm application is produced by linking all klibs at the end (the Kotlin/JS and Kotlin/Wasm compilers consume klib IR and emit one output). An end application therefore always relinks everything and only needs *source* compatibility with the library it compiles against. "Binary" compatibility on klib targets matters for **intermediate libraries and third-party backends that were compiled earlier**. For SpartanGraphics that means SpartanUI's klib (compiled against some `graphics-core`) relinked against a newer `graphics-core`, and any third-party render-backend klib. The single shared version for all artifacts (assumption in the brief) narrows this window without closing it.

Real signatures worth copying:
- `FloatArray.toFloat32Array(): Float32Array` is `actual inline` + `unsafeCast` on JS and a copy loop on `wasmJs` (kotlinx-browser, F6). The cross-target contract is "returns a Float32Array", but the cost model differs; do not put it in a per-vertex loop.
- `kotlin.wasm.unsafe.withScopedMemoryAllocator(block: (MemoryAllocator) -> T): T` and `val wasmMemory: WebAssembly.Memory` (Wasm-JS only, experimental, 2.4.20).
- `buildSrc` pattern in Kool: one `lib-conventions` plugin declares `js` and `wasmJs` together and opts into `kotlin.js.ExperimentalWasmJsInterop` for `jsMain`, `webMain` and `wasmJsMain`.

## 5. Pitfalls and regrets

- **Writing `webMain` against only one target hides breakage.** The 2.2.20 release notes show `Promise<String>` versus `Promise<JsString>` between targets. Code in `webMain` that compiles for `js` only can fail the day `wasmJs` is added. A compile-only `wasmJs` target on `graphics-web` is the cheap guard.
- **Per-element crossing on Wasm.** Kool's regret is visible in its README; a design that streams vertices one at a time into a JS typed array (as Kool's `put` does) turns every vertex write into an interop call. Keep vertex building in Kotlin arrays and cross once per flush.
- **Depending on a date-versioned wrapper in a frozen API.** `kotlin-wrappers` ships monthly and tracks the latest Kotlin (README badge 2.4.21). Hand-written `internal external` GL declarations avoid a transitive version bump leaking into 1.0 consumers.
- **Treating Beta as a 1.0 target without a label.** Kotlin warns Beta may change; Compose's own 1.13.0-alpha01 notes list a Wasm "memory access out of bounds" error. If `wasmJs` is ever published before Stable, label the variant Beta in the README and CHANGELOG.
- **Adding a new abstract member to an interface a third party implements.** Broken on klib backends today (F11). The guard the earlier research already recommends (default bodies, optional sub-interfaces, capability keys) is the right one.
- **Two interfaces gaining the same default.** An old class implementing both fails at runtime with "inherits more than one default implementation" (F11). Capability sub-interfaces should not reuse member names across siblings.
- **Compiler floor on non-JVM.** A library built with a newer language version forces consumers on klib targets onto that compiler or later (F10). Pin `languageVersion` and `apiVersion` low and move them only in a phase-boundary release.
- **JVM-only enforcement ≠ klib enforcement.** BCV and KGP dumps on the JVM do not see klib-only breaks; the klib dump is per target and the tool is experimental (F10).
- **Misreading the Kotlin/Wasm numbers.** JetBrains' "outperforms JavaScript" is a Compose benchmark; do not transfer it to a WebGL renderer (F7).
- **`Long` on JS.** Emulated; avoid it in per-sprite code on the JS-first backend (F7, prior research).

## 6. Recommendation for this repo

### D2: web compilation target and G1's compile check

**Pick (d): Kotlin/JS (IR) first for `graphics-web`, `audio-web` and the fetch `AssetSource`, with `wasmJs` kept reachable, not shipped. G1 adds `js` as the non-JVM target.**

- Reasoning: the web backend's hot path is one large typed-array upload per flush plus tens of GL calls, and that is the one place JS is free and Wasm is not (F6, F7). Kool, the nearest Kotlin peer, ships both, shows its work, and recommends JS. Kotlin/JS is Stable and Wasm is Beta with promotion not yet scheduled (F1). Browser reach is a minor issue for the named consumers, but it is a real cost of `wasmJs`-only (F2), and `js`-only is a real cost only for third-party Compose wasm apps (F8), which are not among the stated consumers.
- G1: `js()` with the default hierarchy template (so `webMain` exists later without restructuring). Use `nodejs()` for `kotlin.test` Level 2 and 4a tests of common code. No `browser()` DOM test infrastructure in G1; the 2.4.20 browser-test DSL is experimental ([what's new 2.4.20](https://kotlinlang.org/docs/whatsnew2420.html), "A new DSL for browser testing"). The reason `js` and not `wasmJs` for G1: coroutines and kotlin-logging support both (F4), so the tiebreak is Stable status, cheaper toolchain, and that G1's target becomes the first web backend's target.
- Web phase mechanics:
  - Put `graphics-web` code in `webMain`. Hand-write the roughly 40 WebGL2 entry points as `internal external` declarations against `JsAny`-compatible types. Do not depend on `kotlin-wrappers` for them.
  - Add `wasmJs` to `graphics-web` as a **compile-only tripwire** (no tests, no sample, publication disabled or labelled) from the start of the web phase, so JS-only assumptions are found before 1.0.
  - Isolate the upload as one `expect`/`actual` seam on `FloatArray` plus a count; the `wasmJs` actual uses the scoped linear-memory path only once someone is benchmarking it.
  - Promotion trigger for publishing `wasmJs`: Kotlin/Wasm reaches Stable (KT-88663) **and** the `wasmJs` backend meets the same web Level 4c gate as `js` on the same machine. Whether this lands before or after 1.0 is then a schedule question, not a design one, because adding a target adds a variant and changes no existing API.
- Rejected: **(c) both from the web phase.** It doubles the Level 4c matrix and the sample app verification for the weaker target, on Beta tooling, for consumers who do not exist yet. **(b) `wasmJs` only.** Excludes older browsers, depends on Beta, and takes the interop penalty on the hottest path. **(a) JS only with no tripwire.** Cheapest now, but it leaves the `webMain` assumptions untested; the tripwire costs one CI job.
- What would change this: a measurement showing `wasmJs` at or above `js` on the 10k-sprite web gate with the linear-memory upload; Kotlin/Wasm Stable; or a named consumer on a Compose `wasmJs` app that needs `graphics-web`.

### D5: the 1.0 binary-compatibility promise off the JVM

**Promise (i) in writing; build (ii)'s enforcement as CI and keep it as the evidence that would justify upgrading the wording.**

- The promise to publish at 1.0: JVM and Android are binary-compatible within a major; JS and Wasm are source-compatible within a major, evolve only additively (new members with default bodies, optional sub-interfaces, capability keys), and an old-implementor relink fixture runs in CI. State plainly that klib binary compatibility follows the Kotlin toolchain, whose own guarantees are "not yet finalized" (F10).
- Reasoning: you can only guarantee what the toolchain keeps. Kotlin's own docs call the klib guarantee unfinalized and the ABI-validation tooling experimental, while partial linkage defers failures to runtime (SILENT log level) (F10, F11). The additive-only rule already in `backend-contract-design.md` §6.4 is exactly the kind of change that the compiler's own tests show surviving a relink (F11), and an abstract addition is exactly what they show breaking. So the engineering discipline is the same under (i) and (ii); only the wording of the guarantee differs, and (i) is the one you can honour if a Kotlin minor changes klib behaviour.
- What G1 should set up (all within existing plan scope):
  - `abiValidation()` on every library module from G1, with the `js` target present so `checkKotlinAbi` produces a `.klib.api` dump; expect to touch the DSL again after 2.4.
  - Pin `languageVersion` and `apiVersion` (the non-JVM compiler-floor rule, F10) and record the floor in the README.
  - After the first backend contract exists (G4), add a **two-version old-implementor fixture** on `js` (and `wasmJs` once it is a real target): a fake backend klib compiled against `graphics-core` N, linked and run (Node) against `graphics-core` N+1. Assert (1) an added default-bodied member is inherited and callable; (2) a deliberately added abstract member fails with the partial-linkage message (a negative control that proves the fixture can fail, and that will flag it if KT-85018 is fixed). I could not find a test that exactly mirrors this, so the fixture is original evidence for this repo rather than a copy of Kotlin's.
- Rejected: **(ii) as a contractual promise at 1.0.** It would put a guarantee in the semver contract that Kotlin has not finalized. The bar to reconsider: JetBrains finalizes klib guarantees (or the fixture has held across at least two Kotlin minor releases and the KGP validation leaves experimental), then the CHANGELOG records the promotion.

## 8. Gaps

- **No measurement exists.** Nobody I found published Kotlin/Wasm versus Kotlin/JS numbers for WebGL calls or typed-array uploads. My "10 to 19 million interop writes per second" is arithmetic on an assumed 4 to 8 words per vertex, not a measurement, and I did not test whether V8 makes each of those cheap enough to be tolerable. The D2 recommendation avoids depending on it but a 30-minute micro-benchmark (naive loop vs linear-memory `Float32Array` view vs JS) on Chrome and Firefox would settle the promotion criterion. This belongs to the render-performance researcher's lane.
- **Kool's JS-over-Wasm advice may predate Kotlin 2.4.** The README sentence was last touched by a commit on or before 2026-05-29 (the file was edited that day, not necessarily that sentence), and Kool's own README also carries the stale "Chrome is still the only browser with WebGPU support". I did not re-run Kool.
- **caniuse figure.** The 92.57% global usage for WebAssembly GC came through a summarising fetcher on `https://caniuse.com/wf-wasm-garbage-collection`; it also reported Chrome/Edge 119, Firefox 120, Safari 18.2 (desktop and iOS), which agree with Kotlin's docs. I have no verbatim quote and the page was not dated. The `Fyrd/caniuse` `features-json/wasm-gc.json` file (commit 2026-09-30) disagrees (Safari unsupported, 76.32%); I judged it stale because Kotlin's docs and the Compose docs both say Safari 18.2 works. Treat the percentage as approximate.
- **Which artifact supplies `org.khronos.webgl` / `org.w3c.dom` to `wasmJs`.** The JS stdlib still contains them at `v2.4.20`; the Wasm stdlib tree has no `org.w3c` directory, and kotlinx-browser (README: "Kotlin `2.2.20-Beta2` or newer", "work-in-progress") provides them. I did not confirm whether the Kotlin Gradle plugin adds kotlinx-browser automatically for `wasmJs` or whether a project must declare it, nor whether declaring it on `js` conflicts with the stdlib copies. Needs a 10-minute scratch project at G1 or in the web phase.
- **Shared `webMain` externals are untested.** I read the release-notes example and the `JsAny` `expect`/`actual`, but built nothing. Whether a ~40-function `internal external` WebGL2 surface (with `ArrayBufferView` and `Float32Array` parameters) compiles unchanged on both targets is unverified. Kool's choice to duplicate its WebGL2 externals per target suggests it might not.
- **No test mirrors the exact D5 scenario.** `severalInheritedImplementations` and `evolutionNewFakeOverride` cover close cases; none covers "new default-bodied member on a public interface, with the implementor in a separate pre-compiled klib that implements only that interface" on JS or Wasm. Section 6 proposes the fixture; until it runs, "default body is safe on klibs" rests on F11 plus the fake-override recomputation note in `KotlinAbiVersionBumpHistory.md`, not on a documented guarantee.
- **KT-85018 could not be read** (YouTrack served an empty page), so I do not know whether the abstract-member break is considered a bug, a limitation, or already fixed on `main` after `v2.4.20`.
- **Gradle resolution of a `js`-only library by a `wasmJs` consumer** is inferred from variant attributes (F8) and not reproduced.
- **Kotlin Slack threads** that the earlier research and I wanted to re-read (Wasm memory API, `ByteArray` on `wasmJs`) returned HTTP 429; I relied on source code and docs instead. The "no fast copy path yet" statement from those threads is not re-verified; the 2.4.20 `wasmMemory` API may have superseded it.
